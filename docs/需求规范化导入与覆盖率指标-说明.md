## 二、规范化前后对比

| 维度 | 规范化前（v1） | 规范化后（v2） |
|---|---|---|
| 章节数 | 10（代码证据聚合） | 21（含文档信息/范围/角色/术语/状态机/NFR/数据字典/依赖假设/待定/质量门禁/追溯矩阵） |
| 验收标准 | 202 条陈述句，**0 条 GWT**，34% 无任何数字或字段锚点 | **218 条 Given-When-Then**，214 条命中 ≥2 级断言锚点（98.2%） |
| 前置条件 | 94/94 全部「用户已登录且具备相应角色」 | 按 **数据 / 权限 / 环境** 三类拆开，且按功能点定制（登出=持有效令牌，登录=匿名可访问） |

| 依赖与假设 | 无 | 91 条，含失效后的降级策略 |
| Out of Scope | 无 | 52 条需求全部显式列出「本次不做」 |
| 术语表 | 无 | 149 个术语，含别名与「禁止使用的同义词」 |
| 变更记录 | 无 | 全部有 v2 变更摘要 |
| 功能条目 | 94 个笼统功能点 | 94 条 FR，每条带角色/入口/触发/三类前置/规则/后置/异常/关联接口与表 |
| 质量分 | v1 文档本身无评分（检查报告按 12 项属性人工评为 49 分） | **均分 81.5**（67–100，机器评分，口径见 §四） |

> 两组分数口径不同：49 分来自《需求文档检查与整改报告》的人工合规度评分，81.5 分来自本工具的机器评分（12 属性 + 11 门禁，且把“用例是否执行通过”计入）。**不要横比涨幅**，应看具体缺口项。

### 关键修正（不是格式美化，是纠错）

1. **角色与接口错配**：v1 按序号机械轮换角色（「失败锁定」派给顾客）、接口按顺序分配（「账密登录」挂到 logout）。v2 改为**按接口所在端（/admin 或 /api）先筛角色，再按语义匹配接口**。
2. **异常张冠李戴**：v1 所有功能点共用同一批异常（「登出」也会列出「密码错误」）。v2 按功能点语义筛选，并补通用边界（分页越界、资源不存在、令牌缺失/过期）。
3. **质量自评虚高**：v2 的质量分把「关联用例是否**执行通过**」计入「正确」「可追溯」两项，所以未验证的需求拿不到满分——分数才有区分度。

## 三、需求覆盖率：当前到底覆盖了多少

指标口径（与规范 §9–10 一致，接口实时计算）：

| 指标 | 含义 | 当前值 |
|---|---|---|
| **需求覆盖率**（主指标） | 已关联测试用例的需求 ÷ 需求总数 | **100.0%**（52/52） |
| **已验证覆盖率** | 有用例「执行通过」的需求 ÷ 需求总数 | **3.8%**（2/52） |
| 追溯覆盖率 | 页面/接口/代码/表 **四层全通**的需求 ÷ 总数 | **94.2%**（49/52） |
| AC 断言锚点率 | 命中 ≥2 级断言锚点的 AC ÷ AC 总数 | **98.2%**（214/218） |
| 文档规范覆盖率 | 有 v2 规范化 PRD 的需求 ÷ 总数 | **100%**（52/52） |

### 用例侧的真实底数

```
在册用例 742 条 → 执行过 8 条 → 通过 2 条 → 从未执行 734 条
（另有 294 条去重合并产生的归档副本，不计入统计）
```

**这就是全部问题的答案**：需求「覆盖」得很好看（每条都有 14–34 条用例），但 **98.9% 的用例从未运行**。文档写得再合规，需求也只是「看起来完成」。

> 口径修正（2026-11-23 追加）：此处原先写作「1036 条 / 未执行 1032 条」，把去重合并后打上 `archived` 标记的 294 条副本也算了进去，导致用例数虚高 40%。`GET /prd/coverage` 已改为只统计在册用例，需求级指标（52/52、2/52）不受影响。基于该口径的回归排期见 `docs/需求回归执行计划.md`。

### 按优先级

| 优先级 | 需求数 | 有用例 | 已验证 | 四层全通 | 需求覆盖率 | 验证通过率 |
|---|---|---|---|---|---|---|
| P0 | 42 | 42 | 2 | 40 | 100% | 4.8% |
| P1 | 9 | 9 | 0 | 8 | 100% | 0% |
| P2 | 1 | 1 | 0 | 1 | 100% | 0% |

**P0 的 40 条未验证需求应优先排期回归**，其中 2 条连四层链路都不全。

### 缺口清单

50 条需求被标记「未完全覆盖」，分布：

- `未验证`（有用例、无通过）：48 条
- `链路断`（四层不全）：3 条（与上重叠）
- `无用例` / `无 PRD`：0 条

完整清单见平台「需求管理 → 需求覆盖率 → 未完全覆盖的需求」。

## 四、质量分分布与未通过的门禁

| 分数段 | 需求数 | 说明 |
|---|---|---|
| 90–100 | 2 | 唯一同时满足「文档合规 + 用例已验证」的两条 |
| 75–89 | 48 | 文档结构合规，卡在「验证覆盖」门禁 |
| 60–74 | 2 | 另有单一性或追溯缺口（如 EXT-AI-001 仅 3 条 AC） |

11 条自动门禁的整体通过率：**500 / 572（87.4%）**。未通过的集中在两类：

1. **验证覆盖**（50 条）：关联用例无一条执行通过；
2. **单一性**（部分）：功能点本身含多动作，如「类目树增删改查」应拆为 4 条需求、「登录、失败锁定、登出」应拆为 3 条。已在文档「遗留与待定」中逐条列出建议拆法。

## 六、限制与需要你确认的点

1. **未把 FR 拆成独立需求**。规范 §4.3 要求「一条需求只描述一个能力」，52 条里有多条不满足（如 V1-FR-001 含 3 个能力）。本次在**条目层**拆成 FR-01..FR-0N 并按 FR 独立判验收，但**没有**在 `requirements` 表里新增子需求行——因为那会打断现有 742 条在册用例的 `requirementId` 关联。如需真正拆分，我可以按 FR 生成子需求并把用例按 `relatedApi` 重新归属（需单独确认）。
2. **NFR 与业务价值是域级模板 + 证据推导**，不是产品原话。目标值（如「登录成功率 ≥ 99%」「列表 P95 ≤ 200ms」）取自代码事实与压测基线，需产品在评审时确认或调整。
3. **质量分是「文档合规度」，不等于「需求业务正确性」**。它衡量的是「能不能评审、能不能验收」，故 81.5 分代表结构达标，不代表需求内容一定对。
4. **用例未执行是外部原因**（执行环境/排期），不是文档问题。要提升「已验证覆盖率」，需要把这 740 条用例纳入回归排期——排期已产出，见 `docs/需求回归执行计划.md`（36 个批次、双轨排期，自动化关键路径约 6 小时可无人值守）。
