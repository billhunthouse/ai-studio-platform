# 需求文档检查与整改报告

> 检查时间：2026-11-23　　检查对象：`ecommerce`（电商核心系统）52 条需求及其已生成的 PRD
> 依据标准：`docs/需求文档规范.md`（ISO/IEC/IEEE 29148:2018 + Gherkin AC + INVEST）
> 检查方式：对 `requirement_prd` 全量结构化统计 + 逐条语义抽查 + 对照 shang-pivot 源码与接口清单核实实现状态

---

## 1. 总体结论

| 指标 | 结果 | 判定 |
|---|---|---|
| 合规度均分 | **49 / 100**（中位 45，最高 60，最低 30） | 无一条达到"可进开发"标准（≥75） |
| 达到 75 分以上的需求 | **0 / 52** | 全部需返工 |
| 验收标准总数 | 202 条（均值 3.9 条/需求） | 数量够，质量不够 |
| 用 Given-When-Then 写的 AC | **0 / 202** | 无法直接转自动化用例 |
| 无量化锚点的弱断言 | 68 / 202（34%） | 不可验证 |
| 前置条件为"用户已登录且具备相应角色" | **94 / 94（100%）** | 模板硬编码，前置分析缺位 |
| 异常/负面场景为空 | 13 / 52（25%） | 负向设计缺失 |
| 目标为套话式一句话 | 38 / 52（73%） | 无业务价值与度量 |
| 缺少的必备章节 | 非功能需求、字段级数据字典、依赖与假设、Out of Scope、变更记录、术语表（**6 类全缺**） | 结构性缺失 |
| 行为验证覆盖 | 19.5 / 52（37.5%，来自 UI 覆盖率报告） | 一半以上需求的行为没有任何断言证明 |

**一句话判断**：现有的"PRD"是**代码证据聚合**，不是需求规格说明。它回答"这个需求关联了哪些接口和表"，但不回答"要做什么、做到什么程度算完成、失败时应该怎样"。

**最关键的发现**：问题的主要矛盾**不是"没实现"，而是"无法证明实现了"**。接口层 48/52 有真实实现，但只有 37.5% 的需求行为有断言验证。这直接导致——**一个真实的高危漏洞（C 端固定验证码）被写成了验收标准，却没有任何一环能发现它**（见 §5.1）。

## 2. 十类问题（按影响排序）

### 2.1 前置条件 100% 模板化（52 条）

现状：94 个功能条目的 `precondition` 全部是「用户已登录且具备相应角色」。

- 登录需求的前置条件写成"用户已登录"——**逻辑上自相矛盾**，登录的前置不可能是已登录。
- 注册、找回密码、游客浏览等场景同样不成立。
- 更严重的是：它掩盖了真正该分析的前置——数据状态、状态机当前态、权限边界、环境依赖。

影响：测试无法据此构造前置，只能凭经验补；需求评审时看不出任何信息量。

### 2.2 验收标准 0 条 GWT，34% 无量化锚点（202 条）

| 类型 | 数量 | 示例 |
|---|---|---|
| 有量化锚点 | 134 | 「密码错误连续 5 次后，第 6 次被锁定 15 分钟」 |
| 无任何数字/字段名 | 68 | 「列表正确展示商品信息」「操作后提示成功」 |

即便有数字的 134 条，也缺三样东西：**前置数据**、**断言落点（表.字段 / 业务码）**、**副作用说明**。

典型案例：「提示成功」——是 HTTP 200？code=0？列表是否刷新？数据是否落库？三个问题都答不上，用例就没法写。

### 2.3 异常与负向场景缺失（13 条为空）

登录、用户管理、角色管理、菜单权限、部门、字典这些 P0 管理端需求，异常场景全部为空。

未覆盖的典型类别：
- 参数非法（必填/类型/长度/枚举）
- 状态不允许（对已删除用户重置密码、对非待发货订单发货）
- 并发（重复提交、并发改同一行）
- 越权（他人资源、跨端令牌）
- 依赖失败（Redis 不可用时的登录行为）

### 2.4 目标为套话（38 条）

例：「让用户安全进入系统，并在失败尝试、令牌时效上具备可预期的行为。」

这是把标题加"让…"拼出来的句子，没有业务价值，也没有度量。规范要求目标必须能回答"不做会怎样"和"用哪个指标衡量"。

### 2.5 非功能需求整体缺失（52 条）

全部 PRD 中**没有任何一条**性能、安全、可用性、兼容性、可维护性指标。后果很直接：

- 登录接口该扛多少 QPS 没人写 → 压测目标无法定义；
- 令牌有效期、密码存储算法没人写 → 安全评审无依据；
- 日志保留、脱敏要求没人写 → 只能靠开发者自觉。

### 2.6 数据字典只到表级（52 条）

`dataModel` 只给出表名与字段类型（`bigint`/`varchar(64)`），缺：必填性、取值范围、枚举全集、默认值、唯一约束、脱敏规则、**不变式**。

不变式缺失的代价已经出现过：`physical_stock ≥ locked_stock ≥ 0` 这类约束如果没有写进需求，库存类缺陷就只能在压测或线上暴露。

### 2.7 需求粒度不单一

典型：「【登录】账密登录、失败锁定、登出」一条需求三个能力；「【商品编辑】SPU + 规格 + SKU 维护」一条需求覆盖三个实体。

影响：一条缺陷无法归属到具体需求；变更时无法评估影响面；覆盖率统计被稀释（一个 partial 掩盖了三个能力）。

### 2.8 角色语义错配

已识别：「失败锁定」被归给「顾客/会员」（实际是管理员登录策略）、「登出」被归给「访客」。角色是按文本片段抽取的，未做语义校验。

### 2.9 两条需求不可作为需求存在

`V1-FR-024`、`V2-FR-026` 是「弹窗与提示规范」，无接口、无页面、无状态，属于**设计规范**而非功能需求。放在需求池里会导致：无法验收、无法计算覆盖、永远挂在"未完成"。

处理建议：移出需求池，作为 UI 设计规范附件，需求侧只保留一条"关键操作用户可感知的反馈提示"并给出可断言清单。

### 2.10 缺"实现状态"与"验证状态"两个维度

当前 `status` 只有"已解析"一种，这是**文档解析状态**，不是实现状态。没有"已实现 / 已验证 / 已关闭"的区分，导致：

- 代码写完了但没验证，也显示"已解析"；
- 验证不通过，也还是"已解析"；
- 37.5% 的行为覆盖率，没有任何机制报警。

## 4. 实现有漏洞的需求清单

> 判定口径：代码逻辑与需求语义/业务常识冲突，或已在压测、实测中复现异常。

### 4.1 【P0·高危】C 端登录验证码可被固定值绕过，且无环境开关

- **相关需求**：V2-FR-001【账号】手机号登录
- **代码位置**：`shang-identity/.../application/CustomerAuthService.java`，`login()` 方法

```java
public static final String DEMO_CODE = "123456";
...
if (!DEMO_CODE.equals(req.getCode()) && (cached == null || !cached.equals(req.getCode()))) {
    throw new BizException(ErrorCode.LOGIN_FAILED, "验证码错误或已过期");
}
```

- **问题**：只要验证码等于 `123456`，第一个条件即为 false，**整个 Redis 校验被短路**。代码里没有任何 `profile`、配置项或开关限制它只在开发环境生效。
- **后果**：任何知道任一手机号的人，输入 `123456` 即可登录该账号；手机号不存在则自动注册。属于认证绕过。
- **需求侧的责任**：需求文档把这行代码写成了验收标准——「AC-03 C 端使用固定验证码 123456 可完成登录/注册」，既没有写"仅 dev/demo"，也没有写"生产必须接入真实短信"。**漏洞是被需求合法化的。**
- **建议**：`DEMO_CODE` 逻辑用配置开关包裹（如 `sms.demo-code-enabled=false` 默认关闭），需求侧改写为两条 AC：开发环境允许固定码；生产环境固定码必须无效且返回 40101。

### 4.2 【P0】登录锁定"15 分钟"的实际窗口小于预期

- **相关需求**：V1-FR-001（AC-02「锁定 15 分钟」）
- **代码位置**：`AuthService.login()`

```java
Long count = redisTemplate.opsForValue().increment(failKey);
if (count != null && count == 1L) {
    redisTemplate.expire(failKey, LOCK_TTL);   // 只在第 1 次失败时设置 TTL
}
```

- **问题**：TTL 在**首次失败**时设置，达到阈值（5 次）时不重置。若用户在 14 分 50 秒内累计 5 次失败，锁只剩 10 秒就自动解除，"锁定 15 分钟"名不副实。
- **实测**：第 6 次确实返回 `40104`（阈值判断正确），但解除时间取决于首次失败时刻，而非达到阈值时刻。
- **需求侧的责任**：AC-02 只写"锁定 15 分钟"，没写**从何时起算**、**达到阈值时是否重置窗口**。规范附录 AC-AUTH-002-2 正是为堵这个洞而设计。
- **建议**：达到阈值时 `expire` 重置为 900 秒；需求补充窗口语义的边界 AC。

### 4.3 【P1】定时任务存在积压与重复执行风险

- **相关需求**：V2-FR-021 超时关单与销量回写、V2-FR-023 定时上架
- **代码位置**：`shang-commerce/.../job/CommerceJobs.java`

```java
@Scheduled(cron = "0 * * * * *")   // 每分钟
... .last("LIMIT 100");            // 单次最多 100 单
... .last("LIMIT 50");             // 定时上架单次最多 50 个
```

- **问题一（积压）**：每分钟最多处理 100 单，上限 6000 单/小时。大促期间待关闭订单积压超过该速率时，关单会持续延后，锁定的库存无法及时释放，进而放大"库存不足"。
- **问题二（重复执行）**：`@Scheduled` 无分布式锁，多实例部署时同一批订单会被多个实例同时处理。是否有幂等保护取决于 `closeAndUnlock` 的实现，需求里完全没有约束。
- **需求侧的责任**：需求只写"超时关单"，没写扫描周期、单批上限、积压告警、多实例幂等要求。
- **建议**：需求补 NFR（单批上限与积压告警阈值、多实例只能有一个执行者）；代码加 ShedLock 或 `SELECT ... FOR UPDATE SKIP LOCKED`。

### 4.4 【P1】商品列表 N+1 查询，并发下打爆连接池

- **相关需求**：V2-FR-004【浏览】分类导航与商品列表
- **代码位置**：`CatalogReadService.productPage()` → `records.stream().map(this::toCard)`，`toCard()` 对每条 SPU 单独查 SKU
- **实测证据**：`/products?page=1&size=20` 单次请求产生 **22.2 条 SQL**（20 条 SPU → 21 次 SKU 查询）；`/categories` 仅 1.2 条。
- **压测表现**：500 并发、思考时间 200ms 时 P95 从 20.8ms 涨到 **1010ms**（放大 88 倍）；`jstack` 显示 400 个 Tomcat 线程中 **374 个（93.5%）阻塞在 `HikariPool.getConnection`**；连接池 pending 峰值 **377**；而 `pg_stat_statements` 里 SQL 平均耗时仅 **0.013ms**。
- **对照实验**：把池子从 20 调到 50，P95 反而更差（1180ms），"拿到连接后的等待"从 247ms 涨到 2313ms——说明瓶颈不是池大小，是借还频率。
- **需求侧的责任**：需求没有性能 NFR，也没有"列表页单次请求 SQL 条数"这类可观测约束，导致问题只能靠压测发现。
- **建议**：批量 `in` 查询（22 → 2）；需求补 NFR：列表接口 P95 ≤ 200ms（500 并发）、单请求 SQL ≤ 3 条。

### 4.5 【P2】只读浏览链路带写事务

- **相关需求**：V2-FR-006【详情】商品详情
- **问题**：浏览商品详情会 `UPDATE browse_history`，纯读流量产生写放大与行锁竞争。
- **需求侧的责任**：需求只写"记录浏览足迹"，没写"是否同步写、是否影响详情页响应时间、写入失败是否影响主流程"。
- **建议**：改为异步写或批量落库；需求明确"足迹写入失败不得影响详情展示"。

### 4.6 【P2】日志全同步刷盘

- **相关需求**：无（属于非功能需求缺失）
- **问题**：logback 所有 appender 均为同步，每请求至少 3 处日志，日增约 133MB。
- **建议**：改异步 appender；需求补"日志异步化、单请求日志条数上限"。

### 4.7 【P2】配置注释与实际生效值不一致

- **问题**：`application.yaml` 注释写 Hikari `max=5`，实际由 `.env` 决定为 `max=20`；Tomcat `maxThreads` 实测 400（非默认 200）。以注释为准会误判容量。
- **需求侧的责任**：非功能需求缺失，导致"以配置注释代替容量基线"。
- **建议**：需求/运维文档统一以 actuator 实测值为准，并在 NFR 中固化基线数字。

## 5. 需求文档缺陷与实现缺陷的因果关系

这份检查最值得记录的一点：**需求文档的质量问题，直接制造了实现层面的盲区。**

### 5.1 把漏洞写成验收标准

`AC-03 C 端使用固定验证码 123456 可完成登录/注册`

- 这句话让"验证码可绕过"从缺陷变成了"符合需求"；
- 它没有环境限定，于是代码里就没有环境开关；
- 它没有负向 AC（"生产环境固定码应失败"），于是没人写这个测试。

一条不合格的 AC，同时放过了设计、开发和测试三道关。

### 5.2 前置条件模板化 → 前置分析缺位

所有需求都写"用户已登录"，等于宣布"前置条件不需要分析"。结果是：状态机前置（仅待发货可发货）、数据前置（库存必须充足）、权限前置（仅本人可查）全都没被识别，也就没被测试。

### 5.3 无实现/验证状态 → 无人报警

37.5% 的行为覆盖率之所以能长期存在，是因为需求状态里没有"已验证"这个可失败的状态。文档说"已解析"，看起来一切正常。

### 5.4 无 NFR → 性能问题只能靠事故发现

N+1、同步日志、定时任务积压，都不是"功能 bug"，而是 NFR 缺位的结果。需求不写指标，就没有验收门槛，也就没有压测目标。
