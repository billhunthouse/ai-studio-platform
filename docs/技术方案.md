### 3.2 核心模块设计

#### （1）模型适配层

统一抽象接口，上层业务不感知底层模型差异：

```python
# app/core/model_adapter/base.py
from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class ChatRequest:
    messages: list[dict]
    model: str
    temperature: float = 0.7
    max_tokens: int = 4096
    stream: bool = False
    tools: list[dict] | None = None  # Function Call

@dataclass
class ChatResponse:
    content: str
    model: str
    usage: dict  # prompt_tokens, completion_tokens
    tool_calls: list | None = None
    finish_reason: str = "stop"

class BaseModelAdapter(ABC):
    @abstractmethod
    async def chat(self, req: ChatRequest) -> ChatResponse: ...

    @abstractmethod
    async def chat_stream(self, req: ChatRequest) -> AsyncGenerator: ...

    @abstractmethod
    async def embed(self, texts: list[str]) -> list[list[float]]: ...

    @abstractmethod
    async def test_connection(self) -> bool: ...
```

模型路由策略：

- 按模型能力标签路由（支持 Vision / 支持 Function Call / 长上下文）
- 失败自动切换备用模型
- BYOK 模式：用户填入自己的 API Key，平台不存储明文（AES 加密存储）

#### （2）RAG 引擎

```
文档上传 → Celery 异步任务
  ├── 1. 文档解析（parser.py）
  │     ├── PDF → pdfplumber / PyMuPDF
  │     ├── Word → python-docx
  │     ├── Markdown → 直接读取
  │     └── 扫描件 → OCR（PaddleOCR）
  ├── 2. 文本切分（splitter.py）
  │     ├── 按标题层级切分
  │     ├── chunk_size=500~1000，overlap=50~100
  │     └── 保留元数据（页码、标题路径）
  ├── 3. Embedding（embedder.py）
  │     └── 调用 Embedding 模型生成向量
  └── 4. 写入向量库（qdrant_store.py）
        ├── collection 按项目隔离
        └── payload: { project_id, doc_id, chunk_index, source_page }

检索流程（retriever.py）：
  用户 Query
    ├── 向量检索（Top-K=10）
    ├── 关键词检索（BM25 / PostgreSQL FTS）
    ├── 合并去重
    ├── Rerank（CrossEncoder 重排序，Top-N=5）
    └── 返回带引用来源的上下文
```

#### （3）工作流引擎

DAG 有向无环图执行器：

```python
# 工作流执行核心逻辑
class WorkflowEngine:
    async def execute(self, workflow_id: str, input_vars: dict):
        # 1. 加载 workflow 定义（节点 + 边）
        # 2. 拓扑排序确定执行顺序
        # 3. 逐节点执行：
        #    - 从上游节点输出取变量
        #    - 构造节点输入
        #    - 执行节点（LLM/HTTP/Code/检索）
        #    - 保存节点输出到上下文
        #    - 通过 WebSocket 推送执行状态
        # 4. 异常处理：节点失败 → 记录错误 → 终止或走异常分支
        # 5. 输出最终结果
```

节点类型：

| 节点 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| LLM | system_prompt, user_query | text | 调用大模型 |
| 知识库检索 | query, kb_id | chunks[] | RAG 检索 |
| HTTP 请求 | url, method, headers, body | response | 调用外部 API |
| 代码执行 | code, input_vars | result | Python 沙盒执行 |
| 条件分支 | condition | branch_a / branch_b | if-else |
| 变量赋值 | key, value | 无 | 设置全局变量 |
| 结束 | output | 最终输出 | 工作流终止 |

### 3.4 API 设计规范

## 四、关键技术难点与方案

### 4.1 LLM 长耗时调用处理

问题：LLM 响应可能 10s+，HTTP 请求会超时。
方案：

- 对话场景：SSE 流式输出，边生成边返回
- 生成用例/接口设计：Celery 异步任务 + WebSocket 推送进度
- 超时兜底：单次 LLM 调用超时 120s，失败自动重试 1 次

### 4.2 多租户数据隔离

- PostgreSQL：每行数据带 `project_id`，查询强制过滤
- Qdrant：每个项目一个 collection，或用 payload filter 隔离
- MinIO：按 `project/{pid}/` 路径前缀隔离

### 4.3 文件解析兼容性

- PDF：PyMuPDF（文本版）+ PaddleOCR（扫描件兜底）
- Word：python-docx，保留表格结构
- 解析失败：记录错误日志，标记文档为"解析失败"，允许手动编辑文本

### 4.4 自动化执行环境

- MVP 阶段：单机执行，Docker 容器内启动 Playwright
- 后期：分布式执行器，任务队列分发到不同 Worker 节点
- 浏览器管理：Playwright 自带 browser pool，避免每次启动浏览器

### 4.5 Token 成本控制

- BYOK 模式优先，平台不承担模型费用
- 平台托管模型：按项目设置 Token 配额，超配额拒绝调用
- 缓存：相同 Embedding 请求缓存 24h
