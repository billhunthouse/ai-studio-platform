> 两件事一起做，因为它们互为前提：
> **不先去重，绑定评审做不动**（363 条没人愿意逐条看）；**不先补 PO，去重后剩下的用例仍然跑不了**（管理端 3 页占缺 PO 清单的 82%）。

> 本文记录决策依据、实现位置、真实执行证据与遗留缺口。所有数字为 2026-11-22 11:30 数据库实测。

## 1. 去重合并

### 1.1 为什么必须做

363 条功能用例只有 69 个唯一标题。副本不是人工重复录入，而是**用例生成器按需求逐条套模板**：一条"库存不变式校验"被挂到 V1-FR-008 ~ V1-FR-013 六个需求下，再跨"商品与类目 / 库存 / 订单交易"三个模块各存一份。

后果不是"数据冗余"这么轻：

1. **UI 自动化的分母被放大 5 倍**——同一条用例跑 23 次，通过率看起来很高，实际只验证了 1 件事；
2. **覆盖统计虚高**——某需求"有用例"，点开发现是别的需求的副本；
3. **人一看 363 条就放弃评审**——绑定确认率永远上不去，因为没人会逐条看 363 条重复的东西。

最大的一个组：`TC-1067 金额合计一致性` 有 **31 条**副本，横跨 8 个模块、31 个需求。

### 1.2 两个口径不要混

| 口径 | 计算 | 数值 | 含义 |
|---|---|---|---|
| 处于重复组的用例 | 363 − 20（单例组） | 343 / 94.5% | "多少条用例有同名兄弟" |
| 冗余副本 | 363 − 69（唯一标题） | 294 / 81.0% | "多少条可以直接归档" |

早期文档写 94.5%，本次写 81.0%，不是数据变了，是**分子不同**。对外说"减少多少条"必须用 294（81%），说"重复问题有多普遍"用 343（94.5%）。

### 1.3 主用例怎么选

选错主用例 = 把有绑定、有执行记录的那条归档掉，等于白干。打分规则（`ui_case_dedup._score`）：

| 信号 | 分值 | 理由 |
|---|---|---|
| 已人工确认绑定 | +200 | 人的判断优先于一切规则 |
| 已有执行记录 | +50 | 有历史可比对 |
| 最近一次通过 | +20 | 基线可信 |
| 状态为通过 | +12 | — |
| 关联需求数 ×3（上限 30） | ≤+30 | 关联多的通常是原始用例 |
| 优先级 P0/P1/P2/P3 | 40/24/10/4 | 同一条被标成多级时取最严 |
| ID 越小 | 微弱加分 | 先登记的通常是原始用例 |

实测结果：49 组全部命中合理主用例。但有一处值得记下来——**20 条曾人工确认的用例里，9 条被归档了**：

| 场景 | 被确认过几次 | 保留 |
|---|---|---|
| 默认地址唯一，设置新默认会取消旧的 | 4 次（TC-1557 / 1653 / 1822 / 1839） | TC-1557 |
| 地址删除无守卫可删默认地址 | 3 次（TC-1569 / 1659 / 1832 / 1849） | TC-1569 |
| 待付款/已关闭订单不能申请售后 | 3 次（TC-1028 / 1470 / 1789） | TC-1028 |
| C 端固定验证码可登录 | 2 次（TC-1073 / 1540） | TC-1073 |

这不是"确认丢了"，是**同一件事被确认了 2–4 遍**：主用例的绑定与流程和被归档副本完全一致，信息无损。
反过来算：此前"19 条确认 / 120 条应绑"里，有近一半是重复劳动——**这正是确认率上不去的隐藏原因**，光靠催着人点确认，越点越亏。

### 1.4 合并做了什么、没做什么

**做**：副本写 `archived=true / duplicateOf / archiveReason / archivedAt`；主用例写 `mergedFrom / mergedCount`，并把副本的**需求、需求标题、模块并集聚合到主用例**（`relatedRequirementIds / relatedRequirementTitles / relatedModules`）。

聚合这一步是关键：合并后 `TC-1067` 一条用例带着 31 个需求、8 个模块。**"一条用例覆盖 6 个需求"这个事实被保留下来**，丢掉只是重复执行，不是覆盖信息。

**没做**：不删除任何记录、不改主用例的 title/steps/expected、不改副本内容。

### 1.5 回滚验证（这是能不能上生产的分界线）

只做"能合并"不够，必须证明"能还原"。实测流程：

```
restore → 294 条副本恢复、49 条主用例清理标记
        → 全量 1042 条用例与备份逐字段比对
```

比对字段：`relatedRequirementIds / relatedRequirementTitles / relatedModules / archived / duplicateOf`。

**结果：字段差异 0 处，用例总数 1042 → 1042。**

要点：有些用例（如 TC-1027）在去重**之前**就人为聚过需求。回滚如果直接 `pop` 这些字段，会把原本合法的关联一起删掉——所以 `apply` 时把原值存进 `dedupPrev`，`restore` 按原值精确还原，而不是清空。

### 1.6 消费侧必须同步改，否则去重等于白做

| 位置 | 改动 | 不改的后果 |
|---|---|---|
| `ui_batch_runner._functional_cases` | 默认排除 `archived` | 编译/执行仍按 363 条跑 |
| `testing._all_functional_cases` | 同上 | `/ui/cases`、`/ui/quality` 分母不收敛 |
| `GET /testcases` | 默认排除，`includeArchived=true` 才返回全量 | 用例列表仍显示 363 条 |
| 用例导出 xlsx | 只导在册 | 评审方分不清哪条是原始用例 |

### 1.7 实现位置

| 文件 | 内容 |
|---|---|
| `backend/app/ui_case_dedup.py` | `plan / apply / restore / summary / is_active`（377 行，新文件） |
| `backend/app/routers/testing.py` | `GET /ui/dedup`、`POST /ui/dedup/apply`、`POST /ui/dedup/restore`、`GET /ui/dedup/groups/{id}` |
| `src/api/webui.ts` | `dedup / dedupApply / dedupRestore` |
| `src/pages/project/UiDedupPanel.tsx` | 去重面板：4 指标 + 明细表（待合并/已归档）+ 执行/回滚 |
| `src/pages/project/UiBindings.tsx` | 挂载面板，合并后联动刷新指标与绑定表 |

明细表在**合并之后**仍然列出全部 49 组（`status=merged`），并保留"当初为什么选它"。合并完就看不到明细，等于让人盲信一次不可复核的操作。

## 2. 管理端 3 个页面 PO

### 2.1 为什么之前缺

管理端是**独立应用**（`shang-admin-web`，端口 5173），与 C 端（`shang-mall`，5174）不同端口、不同登录体系。原 PO 库只覆盖 C 端，于是：

- 缺 PO 清单 85 条里，`/admin/products` 39 条、`/admin/customers` 21 条、`/admin/aftersales` 10 条，合计 **70 条（82%）**；
- 更深的问题：即使补了 PO，执行器的 `baseUrl` 写死 5174，管理端页面根本打不开。

### 2.2 怎么知道该点什么

没有猜，直接探查真实 DOM（Playwright + 管理端账号 `admin / Admin@123`）：

| 页面 | 标题 | 关键元素 | 数据量 |
|---|---|---|---|
| `/products` | 商品列表 | 输入框「商品名称 / 编码」、查询、新增商品、批量下架、行内上架/下架 | 32 SPU |
| `/customers` | 会员管理 | 输入框「手机号 / 昵称」、重置、查询、冻结 | 357 会员 |
| `/aftersales` | 售后管理 | 待审核筛选、行内「审核」→ 售后详情弹窗（同意/拒绝/关闭） | 2 单待审核 |

探查中修正了两个想当然：
- `/products` 搜"手机"是**0 条**（那是类目名，不是商品名），改用 `iPhone`（3 条）；
- 售后点「审核」打开的是**抽屉式详情**，关闭后 `售后单号` 文本消失——正好可以拿来做"关闭无残留"的断言。

### 2.3 四个新 PO 的设计取舍

| PO | 步骤 | 断言 | 关键取舍 |
|---|---|---|---|
| 管理端商品列表流程 | 19 | 8 | 断言"新增商品 / 批量下架 / SPU-SKU 统计"——只有后台才有的东西 |
| 管理端会员管理流程 | 17 | 6 | 断言手机号呈 `****` 形态：**脱敏是安全事故级红线**，比"有数据"更有价值 |
| 管理端售后审核流程 | 21 | 9 | 只打开详情 + 关闭，**绝不点同意/拒绝** |
| 个人中心流程（C 端补） | 14 | 7 | 见 §2.5 |

**为什么售后流程不点"同意"**：那会真实改写售后单状态并触发沙箱退款，不可逆。批量回归里跑一遍就把演示数据打坏一次。这里只验证"审核入口能打开、详情字段齐全、关闭后无残留"——覆盖了交互路径，不产生副作用。

**为什么管理端登录断言从严**：管理端有"连续失败 5 次锁 15 分钟"的风控，登录失败会在批量执行里被放大成一片红。所以断言 `url 含 /dashboard` + 侧边栏渲染，而不是只看"没报错"。

### 2.4 假绿防护：管理端准入闸门

补 PO 带来了一个新风险：**C 端和管理端同名不同站**。C 端也有"商品""售后""订单"，一旦 `/admin/products` 进了候选集，"商品详情页库存展示"就可能被绑到管理端商品列表——跑一遍列表就标通过，又一类假绿。

三道闸门（`ui_bindings.admin_allowed`）：

1. **前台信号一票否决**：标题含 `C 端 / 顾客端 / 前台 / 买家` → 管理端页面直接出局，哪怕标题里也有"上架"；
2. **后台信号准入**：标题含 `管理端 / 后台 / 审核 / 上架 / 下架 / 商品列表 / 会员管理 / 冻结 / SPU / SKU …` → 允许；
3. **模块等级信号**：`RBAC 权限 / 库存 / 评价` 只存在于管理端，不需要标题再自证。

实测命中与拦截：

| 用例 | 闸门判定 | 结果 |
|---|---|---|
| TC-1182「验收点3：**C 端**列表不出现 OFF 或已删除的 SPU」 | 前台信号否决 | 未绑管理端（判待归类）✓ |
| TC-1027「同意/拒绝-主流程成功」 | 后台信号（拒绝/同意） | 绑管理端售后审核 ✓ |
| TC-1090「创建角色时带上 permissionIds」 | 模块 RBAC 仅管理端 | 绑 /admin/roles（缺 PO）✓ |

> 第一版闸门只做了"后台信号准入、没有前台否决"，TC-1182 当场被误绑到管理端商品列表。**错误跑出来的那一刻才算数**——所以闸门是拿真实误绑反推出来的，不是先验设计。

### 2.5 顺手纠正的一处误绑 + 一个产品缺口

`TC-1024「会员等级正确展示」` 原本被人工确认绑到了 `/admin/customers`（管理端会员列表）。核对页面后确认这是错的：管理端列表列是「会员ID / 手机号 / 昵称 / 状态 / 订单数」，**没有"等级"**；会员身份实际展示在 C 端个人中心（`138****0001 · 会员`）。

处置：补 `个人中心流程` PO，用例改绑 `/me`，实测 7/7 断言通过。

顺带发现一个**不是自动化能解决的问题**：需求里有"积分为 0 时显示空状态"（TC-1025），但个人中心页面**根本没有积分模块**。这是页面未实现，不是用例写错。已刻意不让它绑到 `/me`（否则跑一遍"会员标签"就绿了），保留为"待归类"，并在此记录为产品缺口。

## 4. 遗留缺口（不打算糊过去）

| 缺口 | 影响 | 建议 |
|---|---|---|
| `/admin/customers` 有 PO、无用例 | 会员管理流程无人驱动 | 补"会员冻结/解冻、订单跳转"用例 |
| 5 条缺 PO：`/admin/users`×2、`/admin/roles`×2、`/admin/reviews`×1 | RBAC 与评价管理无法自动化 | 优先级低于当前三页，可作下一批 |
| 7 条待归类 | 无明确页面（如"积分空状态"） | 需产品先确认页面是否存在 |
| 个人中心无积分模块 | TC-1025 无法验证 | 产品缺口，已记录 |
| 31 条接口/数据校验用例 | 不该走 UI，当前只标记不执行 | 由 `case_runner` 的接口通道承接 |
| 管理端登录风控 | 批量失败会放大（5 次锁 15 分钟） | 批量执行前先做一次登录探活 |

## 5. 一句话总结

**把 363 条压到 69 条不是"删数据"，是把重复执行去掉、把覆盖信息留下、并且证明能原样退回去；补 3 个管理端 PO 不是"多写几个定位器"，是让 70 条此前跑不了的用例第一次真的跑在被测页面上。**
