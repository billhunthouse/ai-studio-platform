## 3. 自我介绍

### 3.1 30 秒版（面试官刚坐下，只想听你做什么）

> 我最近做的一个项目是 UI 自动化平台。背景是团队有几百条中文测试用例，但 UI 执行一直是人工点，或者接口假装返回成功。我把中文步骤编译成关键字指令，用 Playwright 在真实浏览器里跑，每一步截图加录屏。
> 现在 363 条用例里有 289 条能直接跑，一批几十条 6 分钟出结果，失败能直接指到第几步、页面上实际是什么。

### 3.2 1 分钟版（标准开场，加"难点"体现深度）

> 我做的项目是测试平台里的 UI 自动化执行。
> **问题**：平台有 363 条中文功能用例，但执行是假的——点一下执行，接口永远返回"成功"，其实没启动浏览器，回归还是靠人工。
> **做法**：我把它拆成三层。第一层编译，把中文步骤变成关键字指令，其中抽象步骤（比如"按验收标准核对"）我选择**如实标注为不可执行**，而不是硬转成假点击；第二层执行，用 Playwright 驱动 Chromium，共享一个浏览器进程、每条用例一个独立上下文，只认 9 个白名单关键字，不执行任意代码；第三层留证，每步截图、整段录屏，用签名 URL 给前端直接播，超过 5G 按时间淘汰。
> **结果**：289 条能直接跑，1207 个真实断言，53 条 6 分钟跑完，以前人工要 7 小时。**难点**是 Playwright 的同步 API 和线程绑定，批量任务复用一个浏览器必崩，最后做成每个任务独占一个浏览器池才稳定。

### 3.3 3 分钟版（面试官说"详细讲讲"，或技术面）

在 1 分钟版基础上补三段：

**① 编译为什么不能只用正则**
> 用例里有一半是抽象描述："按验收标准逐项核对""查询订单总额是否等于商品金额之和"。这些不是 UI 操作，硬转就是假自动化。我先做抽象步骤识别，分成设计核对、数据校验、安全探测、业务主流程四类，分别给出处理建议；剩下的才走关键字编译。另外我做了 Page Object，把"登录流程""下单流程"这类 14 个常用流程沉淀下来，命中的用例整体替换成真实操作序列，避免前面那些"输入正确账号密码"编译成占位符、永远跑不了。

**② 执行为什么要有池**
> 启停浏览器是整条链路最贵的操作，一条用例启停一次要 2~3 秒。我改成全局一个 Chromium 进程、每条用例开一个 context 做隔离，用完即关，空闲 5 分钟自动回收。踩的坑是 Playwright 的同步 API 绑定创建它的线程，放进 FastAPI 线程池或后台任务里复用同一个 browser 会抛 greenlet 错，所以后台批量任务必须独占一个池，跑完就关。

**③ 为什么强调"证据"**
> 自动化的信任成本很高——失败了别人第一句就问"是不是脚本问题"。所以我默认每步截图、整段录屏，断言失败必须带实际值，比如"URL 应包含 /pay，实际 /cart"。这样失败可以直接当缺陷附件用。技术细节是 `<img>`、`<video>` 带不了鉴权头，所以我用 HMAC 签名 URL，12 小时过期，既不用放开匿名接口，也不把 token 塞进 URL。

## 4. STAR 深讲（面试官让你"展开说"时用）

**S 情境**
> 平台积累到 363 条中文功能用例，但 UI 执行链路是造假的：接口返回固定结果，没有任何浏览器参与，导致"通过率"没法作为发布依据，回归还是人工点。

**T 任务**
> 让这些用例在真实前端上跑起来，并且做到三点：结果可信（断言基于真实页面）、过程可查（每步有证据）、不能跑的要如实说（不许混进通过率）。

**A 行动**
> 1. **编译层**：抽象步骤先拦截分类 → Page Object 匹配 → 关键字编译成 IR；IR 与框架解耦，同一份能跑也能导出成 Python 脚本。
> 2. **执行层**：共享浏览器池 + 9 个白名单关键字 + 7 种断言（URL/文本/数量/正则），失败快速终止并保留现场；被抽屉遮挡时自动降级强制点击。
> 3. **证据层**：每步截图 + 录屏 + 签名 URL + 5 GiB 预算淘汰，被淘汰的记录标记"媒体已清理"但结论保留。
> 4. **编排层**：单条同步、批量后台任务（轮询）、CLI 三入口共用一套内核；写操作配额保护、按 Page Object 轮转取样、每 10 条落一次库防进程被杀。
> 5. **验证**：真实环境跑批次、写 Playwright 验收脚本逐页检查、做反向验证（故意改坏页面确认断言会失败）。

**R 结果**
> - 289 条用例可直接执行（79.6%），1207 个真实断言；
> - 53 条回归 6 分 12 秒，对比人工约 7 小时；
> - 53 条全通过、565 张截图、53 段录屏、182 个断言全过，失败可定位到具体步骤与实际值；
> - 明确知道短板：95% 时间在固定等待、5% 用例结果不稳、74 条不可执行、没有 CI 和精准回归，并给出了 P0/P1/P2 改进路线。

## 5. 高频追问（16 问 + 建议答法）

**Q1：通过率 100%，是不是没断言 / 刷出来的？**
> 不是没断言，是这批样本恰好都命中了我维护的 Page Object。这一批 53 条跑了 182 个断言，全部基于真实页面元素和 URL，不是接口返回。另外我历史累计执行过 296 次单条，失败过 7 次，所以不是"永远绿"。我之所以敢给 100%，是因为样本里没有产品 bug，失败样本集中在定位器失效上。

**Q2：你怎么证明断言是有效的？**
> 做过反向验证：把页面关键元素/文案故意改坏，断言确实失败；把"下单成功"改成别的文本，`text` 断言立刻报"页面未出现预期文本"。这个做法我只做过一轮，还没固化成每次新增断言都跑，这是我列进改进项的。

**Q3：中文步骤用正则编译，够吗？**
> 不够，所以我没有全靠正则。能覆盖的是标准句式（点击/输入/断言/等待），覆盖不了的是抽象描述，那部分我选择"识别出来并标注"，而不是硬编译。真实数据是 3811 步里 94.2% 可执行，剩下 5.8% 是设计核对项和少量未匹配。要再往上提，得靠 Page Object 覆盖和后面接 LLM 辅助生成候选定位器。

**Q4：为什么不用 pytest-playwright / Allure / Cypress 这些现成的？**
> 现成框架解决的是"写脚本"，我要解决的是"非技术同学在平台上点一下就能跑，并且结果能嵌回用例和追溯体系"。所以执行内核用 Playwright 是对的，但编排、结果落库、证据访问、页面门控得自己写。Allure 报告是后续可以接的，我现在是平台内看，缺一个可分享的 HTML 报告——这也在我改进清单里。

**Q5：跑 100 条要多久？瓶颈在哪？**
> 按实测 6.8 秒/条，289 条约 33 分钟。瓶颈很清楚：我把执行耗时拆开看过，一条 27 步的用例里 18 秒是步骤耗时，其中 11 秒是 `wait`，再加上每步 300ms 节流，**全量算下来固定等待约 33 分钟，等于整个执行时间**。所以第一优先级是把硬等待改成事件驱动等待（等 URL、等元素、等响应），再复用好登录态，目标是压到 10 分钟以内。

**Q6：失败了怎么区分是脚本问题还是产品 bug？**
> 现在靠人看，但我已经把区分所需的证据都留下了：失败步骤的截图、断言的 `detail` 里带实际值（"URL 应包含 /pay，实际 /cart"）、最终页面文本。我统计过历史 7 次失败，6 次能定位到失败步骤，其中 5 次是"找不到元素"，0 次产品 bug——这个结论说明当前失败主要来自定位器，而不是业务缺陷。下一步我会把归因做成自动打标签。

**Q7：flaky 怎么处理？**
> 现在没治理，这是我承认的短板。我量过：120 条被执行过两次以上的用例里，6 条结果不一致，大概 5%。计划是：失败自动重试一次并标记 `retried`、同用例近 10 次结果方差超阈值就进隔离区、单独看板盯，目标是压到 2% 以下。

**Q8：前端改版了怎么办？**
> 定位器集中在 Page Object 的 14 个流程里，改一处全生效，不会散落在 363 条用例里。改完重新编译即可。长期方案是定位器自愈（主定位失败时按文本/role 兜底并记录漂移）和把元素库接进编译链路——元素库现在有 39 个元素登记，但编译没查它，这是个脱节，我已经列进改进。

**Q9：会污染业务数据吗？**
> 会。下单/支付是真实落库的，我的处理是"配额止血"：一次批量最多 3 条写操作（页面可调 8 条），超出的进 skipped 并写明理由，不静默丢弃。但这只是止血，根治要做测试数据工厂——下单前造带时间戳的专属数据，跑完清理，或者接影子库。

**Q10：并发怎么做的？**
> 目前是串行，1 个 worker。原因有两个：Playwright 同步 API 有线程绑定，共享 browser 会崩；写操作并发会撞库存和幂等键。要并发的话按 Page Object 分片、每片独立 browser，写操作用例强制串行互斥，4 个 worker 大概能把 33 分钟压到 9 分钟。

**Q11：元素库和录制回放为什么没接上？**（如果对方看过代码/界面）
> 这两个是平台早期留下的模块：元素库只有登记，编译链路没查；录制回放是前端演示逻辑，没有接 Playwright 的 codegen。我没有把它们包装成"已支持"，因为那属于假功能。要么补齐、要么在界面上标注"未接入"，我倾向先补元素库（改动小、收益直接），录制可以后面接 codegen。

**Q12：和接口自动化怎么分工？**
> 分层。业务逻辑、边界、权限用接口测，快且稳定；UI 只测关键用户路径——登录、搜索、加购、下单、支付、售后这些端到端流程。所以那 74 条"库存校验""金额计算"类的用例，我明确不转 UI，这是判断而不是能力不足。

**Q13：怎么接 CI？**
> CLI 已经具备（`run_ui_batch.py --limit 120 --max-write 8`），与接口共用同一套内核，接 Jenkins 或 GitHub Action 只是加一步调用 + 解析退出码。门禁我会分两级：PR 跑 20 条冒烟（3 分钟内），主干每日跑全量。

**Q14：这个项目最难的点是什么？**
> 不是写 Playwright，是"让结果可信"。三个坑：一是抽象用例不能硬转，否则通过率是假的；二是 Playwright 同步 API 的线程绑定，批量任务必须独占池；三是证据访问——`<img>/<video>` 带不了鉴权头，最后用 HMAC 签名 URL 解决，还要防止 `../` 穿越。这三件事决定了它是"能演示"还是"能给别人用"。

**Q15：重来一次你会怎么设计？**
> 我会先做两件"地基"的事，再写执行：第一，用例和页面显式绑定（现在靠标题关键词猜），有了它才能做精准回归和覆盖率；第二，度量体系先立起来（flake rate、失败归因、时长 P95），否则改完不知道有没有变好。执行引擎反而是最容易的部分。

**Q16：为什么只有八成能跑？剩下两成呢？**
> 剩下 74 条是业务规则、权限、数据一致性类用例，比如"库存扣减是否原子""越权访问是否被拦截"。这些不是 UI 操作能验证的，强行做成"点一下就算过"才是灾害。我的口径是：UI 覆盖关键链路，其余交给接口和 DB 断言。

## 8. 一句话收尾（面试结束前可主动说）

> 这个项目我最满意的不是跑通了多少条，而是**它不会骗人**：跑不了的会标出来，失败会说清实际是什么，证据能回溯到某一步。自动化最怕的不是慢，是"绿得没有意义"。
