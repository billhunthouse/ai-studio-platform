# UI 自动化执行架构设计说明

> 目标：把功能测试用例的中文步骤转化为可复用、可真实执行的 Playwright 脚本；
> 点击执行即在真实前端（尚品汇 127.0.0.1:5174）上跑，步骤间 300ms 延时。
> 架构原则：**一次编译、处处复用；共享资源、按需回收；诚实标注、不伪造自动化**。
>
> 📘 想直接上手使用 / 了解技术选型理由，请看 **[`UI自动化执行-技术方案与使用手册.md`](./UI自动化执行-技术方案与使用手册.md)**；
> 本文是演进过程与踩坑记录（按时间追加）。

---

## 1. 现状与目标

### 1.1 改造前的假实现
- `POST /ui/runs` 永远返回 `result="成功", shots=3, duration="36s"`——纯造假，不接触浏览器。
- 元素库只有 4 个名字、locator 全空，无法作为定位来源。
- 399 条功能测试用例步骤是中文自然语言，其中 350 条来自测试工程师 AGENT，
  步骤多为抽象描述（"按验收标准构造场景"、"逐项核对验收标准"），
  **本质上不是 UI 操作指令**。

### 1.2 目标
| 维度 | 要求 | 实现 |
|---|---|---|
| 真实执行 | 点击执行跑真实浏览器 | Playwright Chromium → 尚品汇前端 |
| 节流 | 步骤间 300ms | 执行器统一 `wait_for_timeout(300)` |
| 不浪费资源 | 避免每用例启停浏览器 | 共享浏览器池：1 browser + N 临时 context |
| 可复用 | 脚本可编辑、导出、重跑 | 编译产物落 `uiScripts`，IR 与实现解耦 |
| 诚实 | 不能执行的明确标注 | 抽象步骤分类为 design_check，不伪装成通过 |

## 2. 分层架构

```
功能测试用例（中文步骤 + 预期）
        ↓ 编译一次
步骤编译器 ui_step_compiler.py
   中文 → 关键字 IR（nav/click/fill/assert…）
        ↓ 生成
Playwright 脚本 → uiScripts（可编辑/导出/复用）
        ↓ 执行
执行引擎 ui_executor.py
   ├─ 关键字执行器：只认有限关键字，不 eval 任意代码
   ├─ BrowserPool：1 browser + N context（共享、空闲回收）
   └─ 节流：步骤间 300ms，失败快速终止 + 截图
        ↓ 回写
uiRuns 执行记录 + 用例 lastRun + 详情页步骤轨迹
```

### 2.1 步骤编译器（`backend/app/ui_step_compiler.py`）
- **关键字 IR** 是中间层：与具体浏览器框架解耦，同一 IR 未来可生成 JS/其他框架脚本。
- 12 类关键字：`nav / click / fill / select / check / assert / wait / scroll / screenshot / design_check`。
- 中文规则匹配：正则 + 语义定位器词典（"登录按钮" → `button:has-text('登录')`）。
- **抽象步骤分类**（关键设计）：不把"按验收标准核对"硬转成假点击，而是分四类标注：
  - `design_check`：验收核对项，需业务专家补全定位器；
  - `db_verify`：数据校验项，建议 API/DB 断言（非 UI 操作）；
  - `security_probe`：安全探测项，需专用数据与权限环境；
  - `business_flow`：业务主流程，建议拆成多个页面对象步骤。
- 编译结果含 `ready / uiRunnable / designChecks / unknown` 四维统计，诚实反映可执行度。

### 2.2 共享浏览器池（`backend/app/ui_executor.py::BrowserPool`）
- **单例**：全局 1 个 Chromium 进程，避免最昂贵的启停操作。
- **context 隔离**：每条用例一个独立 `browser.new_context()`（cookie/localStorage 隔离），
  用完立即 `close()`，`activeContexts` 计数受控。
- **空闲回收**：`idle_ttl=300s`，空闲超时且无活动 context 时自动关浏览器。
- **可观测**：`GET /ui/pool-status` 返回 `browserAlive / activeContexts / idleSeconds`。
- 失败自动截图（仅失败时写盘），成功不产生文件。

### 2.3 关键字执行器
- 只执行编译后的有限关键字，不执行用户自由输入的任意代码（安全边界）。
- 每个关键字超时受控（click 5s / nav 10s），失败快速终止当前用例，不浪费后续步骤。
- 步骤间统一 `waitForTimeout(300)`；`wait` 关键字自身已等待时不重复。
- 定位失败返回 `failed` 并给出具体 locator，便于补全。

## 3. 数据模型

| 集合 | 新增字段 | 用途 |
|---|---|---|
| `uiScripts` | `caseId`, `caseTitle`, `ir`, `framework="Playwright · 关键字驱动"`, `status` | 编译产物，可编辑复用 |
| `uiRuns` | `caseId`, `verdict`, `steps[]`, `screenshot`, `duration` | 真实执行记录（替代原假数据） |
| `testCases` | `lastRun{mode:"ui", verdict, at}` | 用例页展示最近一次 UI 执行结果 |

---

## 4. API 设计

| 端点 | 方法 | 说明 |
|---|---|---|
| `/ui/compile` | POST | 批量编译功能用例→IR+脚本；`caseIds` 空=全部，`overwrite` 控制重编译 |
| `/ui/compile/{case_id}` | GET | 查看单条编译结果（IR + 脚本源码） |
| `/ui/run-cases` | POST | 共享浏览器池执行；`caseIds` 指定用例，`delayMs` 默认 300 |
| `/ui/pool-status` | GET | 浏览器池资源状态 |

## 5. 前端交互

- **Web UI 自动化 → 用例脚本页**：新增执行台（编译按钮 / 执行按钮 / 四类统计 / 用例列表 / 步骤轨迹 / 脚本编辑器），
  替换原"运行永远成功"的假逻辑。
- **测试用例详情页**：功能用例执行面板新增「编译并自动执行」按钮，
  展示每个步骤的关键字与状态（通过/失败/待补全），并把结果回写 `lastRun`。

## 8. 元素库与 Page Object 补全（2026-11-21 续）

### 8.1 问题
首版编译 363 条用例**无一完全可执行**——990 个步骤是抽象描述
（"按验收标准构造场景"、"执行被测操作"），只补 locator 无法解决，
因为用例本身没有具体 UI 动作。

### 8.2 方案：从真实前端代码反推 PO
- **元素库**（`backend/gen_ui_elements_from_source.py`）：
  解析 shang-mall 的 21 个 Vue 页面模板，提取 35 个真实元素的
  placeholder / button 文本，每个带 `sourceFile` 证据，落 `uiElements` 集合；
  14 条路由落 `uiRoutes`。
- **Page Object**（`backend/app/ui_page_objects.py`）：
  把高频业务封装为 10 个可复用流程（登录/搜索/加购/结算/下单/支付/订单/售后/收藏/地址），
  每个 PO 是 nav/click/fill/wait 序列，定位器来自元素库，演示数据来自真实 DDL/源码
  （手机号 13800000001、验证码 123456——LoginForm.vue 明示"演示环境固定 123456"）。
- **编译器增强**：`compile_case` 遇到抽象步骤时按 module+title 匹配 PO，
  展开为具体 UI 步骤替换原抽象步骤；业务规则类（库存/RBAC/全站规范）保留 design_check，
  标注走 API/DB 执行器而非伪装 UI 自动化。

### 8.3 效果
| 指标 | 首版 | PO 补全后 |
|---|---|---|
| 完全可执行 | 0 / 363 | **282 / 363** |
| 需 API/DB 校验 | — | 81（合理保留） |
| 真实浏览器执行（8 个 PO 代表用例） | — | **8/8 通过** |

### 8.4 踩坑与修正（真实执行暴露）
1. 首页商品链接文本是价格（¥7999.00）而非商品名 → PO 改为直接 `nav("/product/101")`
2. 订单/售后/支付/结算页游客会被重定向到登录页 → 这些 PO 前置 `flow_login()`
3. 演示数据里订单多为"已完成"，无待付款可点 → 支付 PO 改为直接导航收银台验证页面可达

结论：**只有真实执行才能验证 PO 正确性**——静态编译的"可执行"不等于真能通过。

## 9. 真实场景验证与 v2 重构（2026-11-21 续）

### 9.1 结论

| 指标 | 数值 |
|---|---|
| 功能用例总数 | 363 |
| 编译为完全可执行（PO + 真实断言） | **289** |
| 真实执行（逐条开浏览器跑） | **120** |
| 通过 / 失败 | **120 / 0**，通过率 100% |
| 业务断言 | **456 个全部通过** |
| 真实写操作落库 | **22 笔订单**（`commerce.order`，状态 PENDING_SHIP） |
| 反向验证 | 破坏定位器/断言 → 必然失败；恢复 → 通过 |

### 9.2 v1 为什么是"假通过"

静态看 282 条"完全可执行"，真实跑之前用 Playwright 逐页 dump DOM 才发现，v1 的 PO 有 5 处根本没做到它声称的事：

1. **同名元素命中两个**：商品详情页同时存在"页面主体"和"SKU 抽屉（`van-popup`）"两套 `chip` 与「加入购物车」按钮。
   `button:has-text('加入购物车')` 命中 2 个元素，Playwright 取第一个（被抽屉遮罩）→ 点击 5s 超时。
   v1 的 PO 里没有任何断言，这种超时被计入"步骤失败"却仍可能被看作场景跑过。
2. **未选规格加购会被业务拦截**：实测点击后弹「请选择规格」弹窗，购物车角标 32 → 32 不变。
   v1 的流程等于什么都没做。
3. **提交订单有二次确认**：点「提交订单」→ 弹「取消 / 确认提交」→ 再点才真正创建订单。v1 只走到第一步。
4. **立即购买还有一层弹窗**：选规格 → 立即购买 → 「确认下单信息」（再想想 / 去确认订单）→ `/checkout?spuId=101&skuId=10001&quantity=1`。
5. **收银台进入即自动模拟支付**：`/pay/{orderId}` 页面直接展示「支付成功 · 订单号 O… · 待发货」，无需再点支付。

> 共同点：这些都**不抛异常**。只看"步骤没报错"，失败会被判成通过。这正是必须有业务断言的原因。

### 9.3 v2 的四处改造

1. **Page Object v2**（`app/ui_page_objects.py`）：13 个流程，所有规格/操作定位器 scope 到 `.van-popup`，
   覆盖"抽屉 → 规格 → 立即购买 → 确认下单信息 → 确认订单 → 提交 → 二次确认 → 收银台"全链路；
   每个 PO 自带业务断言（登录离开 `/login` 且出现「Hi，」；搜索有商品链接；下单跳 `/pay/` 且出现「订单号」）。
2. **断言引擎**（`app/ui_executor.py::_run_assert`）：`url` / `url_not` / `text` / `no_text` / `count` / `regex`，
   失败时把**实际值**写进 detail（如「页面未出现预期文本 X」「URL 应包含 X，实际 Y」），而不是只报一句失败。
3. **编译策略**：命中 PO 时**整条替换**（原中文步骤折叠进 `originalSteps` 保留意图），
   不再把"输入正确账号密码"这类笼统步骤与 PO 拼接造成 `{{TEST_VALUE}}` 占位。
4. **执行架构**：
   - 后台任务（`POST /ui/run-batch` + 轮询），100+ 条不再撞 HTTP 超时；
   - 每个任务独占一个 `BrowserPool(isolated=True)`——Playwright sync API 与创建它的线程绑定，跨线程复用同一 browser 会崩；
   - 写操作用例配额（`--max-write`），避免耗尽演示库存/污染订单表；
   - 通过用例也截图，结果带 `finalUrl` / `pageText` / 断言通过数，便于人工抽查。

### 9.4 反向验证（mutation test）

| 实验 | 改动 | 结果 | 实际错误 |
|---|---|---|---|
| A 基线 | 原样执行 | 通过 | — |
| B 破坏定位器 | 手机号输入框改成不存在的选择器 | **失败** | 找不到输入框：`input[placeholder='这个输入框不存在']` |
| C 破坏断言 | 断言文本改成页面上不可能出现的字符串 | **失败** | 页面未出现预期文本「…-XYZ」 |
| D 恢复 | 还原后重跑 | 通过 | — |

如果 B/C 也能"通过"，说明执行器在自欺。实验结果证明执行是真的、断言是生效的。

### 9.5 平台化：三个入口，一套内核

| 入口 | 用途 | 关键实现 |
|---|---|---|
| CLI | 批量回归、CI | `backend/run_ui_batch.py` |
| HTTP | 平台驱动 | `POST /ui/run-batch`、`GET /ui/run-batch/{jobId}`、`POST /ui/compile-all` |
| 界面 | 人工触发与查看 | 前端「WebUI 自动化 → 用例脚本 → UI 自动化执行台」：条数/配额输入、进度条、按 PO 汇总、失败明细、逐条证据 |

三者共用 `app/ui_batch_runner.py::execute_batch`，避免行为漂移。

### 9.6 边界（不夸大）

1. **UI 只覆盖用户可见结果**：如"库存 locked 增加""金额一致性"属 DB/API 断言，本报告不算 UI 通过；
   74 条业务规则/权限类用例仍保留 `design_check`。
2. **PO 是路径级复用**：同一条 PO 会被多条用例复用，覆盖"正常路径"，不等于每条用例独有的异常分支。
3. **同一条 PO 的断言是页面事实**：如"订单创建后库存扣减"跑的是下单流程，断言的是"订单创建成功"，
   库存数值断言需 API/DB 层补齐——这是分层测试的正常分工，但不能说成 UI 已验证库存。

完整数据：`docs/traceability/ui-real-run-final.json` / `.md`、`ui-negative-verify.json`。

## 10. 单条用例执行：在页面上跑一条（2026-11-21 续）

批量回归解决"一次跑 100+ 条"，但日常调试最常做的是"就这条，跑一遍给我看每一步"。
第 9 章只有批量入口，单条得先编译、再整批跑，既慢又给不出逐步细节。本章补上单条链路。

### 10.1 两个接口

| 接口 | 作用 | 说明 |
|---|---|---|
| `GET /ui/cases` | 单条执行的用例索引 | 现场编译一遍（363 条约 30ms），返回 `pageObject / ready / writeFlow / 步数 / 断言数`，**不落库**，所以不必先点"编译全部" |
| `POST /ui/run-one` | 真实执行一条并回放 | 入参 `{caseId, delayMs?, force?}`，同步返回逐步状态、断言、`finalUrl`、`pageText`、订单号、截图 data URL、本次执行脚本 |

`run-one` 做的事：`must_doc` 取用例 → `compile_case` 现场编译 → 隔离池 `BrowserPool(isolated=True)` 跑 `run_compiled`
→ 写操作回查 `commerce.order.order_no` → 截图转 base64 → 落库 `uiRuns` + 回写用例 `lastRun(mode=ui)`。

**为什么现场编译而不读 `uiScripts`**：`uiScripts` 依赖"先编译全部"，页面冷启动时是空的；
编译本身只是字符串处理，代价可忽略，现场编译能让"打开页面→选一条→跑"零前置条件。

### 10.2 安全守卫

| 风险 | 守卫 |
|---|---|
| 误点下单/支付产生真实订单 | `summary.writeFlow` 为真时 `force=false` 直接 `409`，页面按钮置灰并提示勾选"允许真实写操作" |
| 用例只有业务规则描述、没有 UI 步骤 | `uiRunnable=false` 返回 `400`，不启动浏览器 |
| 跨线程复用一个 browser 崩掉 | 每次请求自建隔离池，`finally` 里 `pool.close()`；`/ui/run-cases` 同步改造成同样隔离 |
| 截图无法鉴权访问 | 不回传文件路径让前端取，直接把 PNG 转 data URL 放进响应 |

### 10.3 页面上的两个入口

1. **WebUI 自动化 → 用例脚本 → 「单条用例执行」卡片**（页首）
   搜索框（用例 ID / 标题 / 模块）→ 列表选中 → 「运行这条用例」→ 回放卡片：
   结论 / 步骤通过数 / 断言 / PO 四格 + 逐步表格（序号、用例原文、关键字、耗时、详情）
   + 点开某一步看**实际定位器与输入值**（`locator=input[placeholder='请输入 11 位手机号'] · value=13800000001`）
   + 最终页面、页面文本前 300 字、真实订单号、截图缩略图（点击放大）、本次执行脚本（Monaco）。
2. **测试用例 → 用例详情 → 「运行这条用例的 UI 步骤」**
   不离开用例上下文就能跑，同样展示判定、逐步状态、断言、最终页面、订单号与截图。
   深链 `?caseId=TC-1001` 可从任意页面直达并自动选中。

### 10.4 实测（真实环境，2026-11-21 17:2x）

| 场景 | 结果 |
|---|---|

## 11. 执行记录与用例列表改造（2026-11-21 晚）

### 11.1 页面结构

| 项 | 改造前 | 改造后 |
|---|---|---|
| 页签顺序 | 元素库 / 用例脚本 / 录制回放 / 执行记录 | **用例脚本 / 执行记录 / 录制回放 / 元素库** |
| 副标题 | "维护元素库、脚本、录制与执行记录" 等小字 | **删除**（`PAGE_HINTS` 不再给 webui 文案，空则整行不渲染） |
| 执行记录排序 | 按入库顺序 | **按开始时间倒序**（`startedAtMs`，历史数据兜底 `time`） |
| 批量执行 | 每条用例各占一行 | **折叠为一条批次记录**，点进 `/webui/runs/{batchId}` 看逐条明细 |
| 单条执行 | 一行 + 抽屉 | 一行 + 抽屉，**抽屉内逐步截图 + 视频** |

### 11.2 每步截图与视频（默认保存）

执行器 `run_compiled(..., run_id=...)` 在每次执行时：

1. `BrowserPool.acquire(video_dir=...)` 用 `record_video_dir` 录 webm（800×500，约 0.1~0.3MB/s）；
2. 每个步骤结束后截一张 `step_NN.png`（1440×900，约 40~300KB），失败也留证；
3. `context.close()` 后把 Playwright 随机命名的视频改名为 `video.webm`；
4. 返回 `media: {dir, video, bytes, steps:[{index,name}]}`，落库到 `uiRuns` / `uiBatches`。

目录：`/tmp/ui-auto-media/{runId}/`，一次执行一个目录；批次的每条用例是 `{batchId}__{caseId}/`。

### 11.3 媒体访问：签名 URL，而不是放开鉴权

`<img>` / `<video>` 无法带 `Authorization` 头。做法：`GET /api/v1/ui/media/{run_id}/{name}?k={exp}.{hmac}`

- 签名 = HMAC-SHA256(app_secret, `{runId}/{name}:{exp}`)，有效期 12 小时；
- 拒绝 `../` 穿越，只允许取目录内文件；无签名/过期 → 403，文件不存在 → 404；
- 用 `FileResponse` 返回，**支持 Range**（实测 `206 Partial Content`），视频可拖动进度条。

没有采用 base64 内联：一条 7 步用例的截图 + 视频约 1.5MB，内联会把响应撑爆，且无法流式播放。

### 11.4 5GB 容量策略

`app/ui_media.py`：

- `BUDGET_BYTES = 5GiB`，每次单条/批次执行结束调用 `prune_and_mark()`；
- 按目录 mtime 从旧到新删除，直到总大小回到预算内；
- 被删的 runId 在 `uiRuns` / `uiBatches` 上标 `mediaPruned=true`，页面显示"媒体已按 5GB 容量策略清理"，**执行结论与步骤状态保留**，不是把历史记录整条删掉；
- 页面顶部展示 `媒体占用 12.0 MB / 5.0 GB`。

淘汰逻辑用小预算做过验证（把预算临时改成 3KB）：4 个各 1.2KB 的目录按时间从旧到新被删，剩余总量回到预算内。

### 11.5 勾选多条 → 一次批次

- 用例列表每行前置复选框，表头可全选（当前筛选结果）；
- 「执行选中 N 条」：N=1 走单条同步回放；N>1 走 `POST /ui/run-batch`（后台任务 + 轮询），完成后出现「查看批次详情」直达子页面；
- 写操作用例需勾选「允许真实写操作」，否则按钮拦截；
- 勾选了但未转化为自动化脚本的用例不会静默丢弃：批次详情的「未执行」卡片写明 `尚未转化为自动化脚本（缺少 Page Object / 可执行步骤）`。

批次落库：开始时写 `uiBatches{status:running}`，每 10 条刷新一次进度（避免 120 条时反复写大 JSON），结束时写完整汇总；进程被杀也能留下已完成部分。
