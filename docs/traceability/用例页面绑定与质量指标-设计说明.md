# 用例-页面绑定与质量指标 · 设计说明

> **版本说明（2026-11-22 11:30 追加）**
> 本文记录的指标是**去重前基线**（363 条功能用例、绑定确认率 15.8%、页面 PO 覆盖 34.1%）。
> 同日已完成两件后续工作并落库：① 重复用例去重合并（363 → 69）；② 补齐管理端 3 个页面 PO 与 C 端个人中心 PO。
> 去重后的指标与本轮决策依据见 `用例去重与管理端PO补齐-实施说明.md`；
> 本文的**问题诊断与设计原理仍然有效**，只是数字需按下文新文档的口径理解。

> 解决两个问题：
> ① **通过率不可信**——"53 条全绿"里有多少是真的验证了用例意图？
> ② **用例和页面是拆的**——只靠标题关键词猜绑定，既说不清"测哪个页面"，也做不了精准回归。
>
> 本文既给设计，也给已落地的实现位置和人工操作路径。所有数字来自当前数据库实测（2026-11-22）。

## 0. 先说三个结论

**结论一：当前"97.8% 通过率"不能对外用。**
363 条功能用例里，242 条（66.7%）被规则绑定到了与该用例意图无关的 Page Object。典型例子：

| 用例 | 实际步骤 | 被展开成 | 结果 |
|---|---|---|---|
| TC-1067 金额合计一致性（明细小计之和 = 订单总额 + 运费） | 查询订单 total_amount / 逐条取 subtotal / 手工计算核对 | 订单列表流程（打开 /orders → 搜索 → 断言页面存在） | 通过，4 个断言 |
| TC-1003 订单创建后库存扣减 | 下单后查库存 | 完整下单流程 | 通过，6 个断言 |

它们跑的是**一个维护良好的稳定流程**，所以必然通过；但用例真正要验的金额关系、库存扣减**一个字都没验**。这类"绿"是假绿。

**结论二：用例总量是虚的。**
363 条功能用例只有 **69 个唯一标题**，343 条是副本（94.5%）。同一个验收点被复制到 8 个模块下，步骤完全相同。真实场景覆盖是 69，不是 363。

**结论三：不可执行不是黑盒，可以拆成四种可派活的缺口。**
220 条本质是接口/数据校验（不该走 UI）、85 条页面已知但缺 PO、7 条页面有多个流程待选定、8 条需人工、15 条待归类。拆开之后，"为什么跑不了"每一类都有明确的下一步动作，而不是笼统的"未自动化"。

## 1. 问题本质：三层之间没有边

现在系统里同时存在三份数据，但它们之间**只有字符串包含关系**：

```
用例 1042 条（363 功能）        页面 41 个              Page Object 14 个
   module + title      ← 猜 ←     路由路径        ← 硬编码 ←   流程函数
        ↑                                                          ↑
        └──────────── match_po(module, title) 关键词命中 ───────────┘
```

`match_po` 的实现是：标题里出现"订单"就返回"订单列表流程"，出现"支付"就返回"收银台支付闭环"。这带来三个结构性缺陷：

| 缺陷 | 表现 | 后果 |
|---|---|---|
| 无法正向回答 | 这条用例测哪个页面？ | 只能看 module 猜，module 是业务域（"商品与类目"跨 5 个页面） |
| 无法反向回答 | 这个页面被哪些用例覆盖？ | 改了一个页面，不知道该回归哪些用例，只能全量跑 |
| 误命中无成本 | "取消收藏"命中"取消订单" | 跑通即标通过，错误绑定不会暴露 |

**所以修法不是"把关键词规则调准"，而是把绑定升级为一等数据。**

## 2. 绑定模型：三层、六分类、一个状态机

### 2.1 三层关系

```
        TESTS                    IMPLEMENTED_BY
用例 ──────────→ 页面 ─────────────────────→ Page Object
(TC-1001)      (page:mall:/login)            (登录流程)
   权威                 稳定锚点                    可重构实现
```

设计取舍：

- **绑定绑页面，不绑 PO。** 页面路由是稳定锚点（`/cart` 改版也还是 `/cart`），PO 是会重构的实现细节（`flow_cart` 可能拆成两个流程）。用例只声明"我在哪个页面验证"，PO 由「页面 + 标题意图」推导。
- **一个页面可以有多个 PO，一个 PO 可以覆盖多个页面。** 例如 `/cart` 同时是「购物车流程」和「购物车结算流程」的入口；「完整下单流程」可以从 `/product/:spuId` 或 `/checkout` 发起。这层多对多用 `PO_PAGES` 表表达。
- **页面没有 PO 是可表达的状态**，不是错误。这类用例进"缺口清单"，回答的是"缺哪个页面的自动化"，而不是"没自动化"。

### 2.2 六分类

不再是"可执行 / 不可执行"二元，而是六种可命名、可派活的类：

| kind | 含义 | 进 UI 队列 | 计入有效通过率 | 下一步动作 |
|---|---|---|---|---|
| `ui_po` | 页面已定位 + 流程可确定 | ✅ | ✅ | 跑 |
| `ui_page_no_po` | 页面已定位 + 该页确实没有 PO | ❌ | ❌ | 写该页 PO，写完自动转为可执行 |
| `ui_ambiguous` | 页面有多个 PO，标题分不出走哪个 | ❌ | ❌ | 人选一个流程（弹窗单选） |
| `api` | 接口/数据校验 | ❌ | ❌ | 转接口自动化，不进 UI 队列 |
| `manual` | 视觉/规范/探索 | ❌ | ❌ | 人工或截图比对 |
| `unbound` | 判不出 | ❌ | ❌ | 人工指定页面 |

> `ui_page_no_po` 和 `ui_ambiguous` 必须分开：前者要"写代码"，后者只要"点一下"。混在一起会让人以为 85 + 7 条都要补 PO，实际只有 85 条要。

分类判定顺序（`ui_bindings.suggest`）：

```
1. 命中数据特征词（金额/库存/脱敏/幂等/SQL/返回 400/并发/精度/一致性）
   且没有明确 UI 动作词  → api
2. 命中视觉规范词（文案一致/布局/视口/H5/探索）  → manual
3. module → 候选页面集 → 标题意图在候选里打分 → 选页面 → 页面反查候选 PO
   - 有 1 个 PO              → ui_po
   - 有多个 PO 且标题能挑出   → ui_po
   - 有多个 PO 但挑不出       → ui_ambiguous（需人选流程，不硬猜）
   - 该页没有 PO             → ui_page_no_po
4. 标题没有任何页面线索（纯靠 module 兜底）  → unbound
```

**关键设计：低置信度时宁可不给建议。** 早期版本对"下单快照一致性"这种标题靠 module 兜底给了"售后管理"页（明显错），后来改成 `best_score == 0 → unbound`。给一个错页面比不给更糟：人会以为机器判断过了。

实测分布：

| 分类 | 条数 | 占比 |
|---|---|---|
| 接口/数据校验 | 220 | 60.6% |
| 缺 Page Object | 85 | 23.4% |
| 可执行 | 28 | 7.7% |
| 待归类 | 15 | 4.1% |
| 人工验证 | 8 | 2.2% |
| 待选流程 | 7 | 1.9% |

> 这个分布本身就是结论：**当前项目真正可执行的 UI 自动化只有 28 条用例**。之前"289 条 ready"是把 220 条接口类用例硬套 PO 换来的。

### 2.3 绑定状态机（谁说了算）

```
            规则建议                     人工确认
  (无) ──────────────→ rule(待确认) ──────────────→ human(权威)
   ↑                        │                          │
   └──────── 解除绑定 ───────┴──── 页面/PO 下线 → stale_po / blocked_no_po
```

- **`rule` 只是建议，编译不采信。** 编译时若 `bindingSource != human`，仍走旧的 `match_po` 兜底（保证零回归），但结果里标 `risk=guess | mismatch`，前端显示红/黄点。
- **`human` 权威。** 一旦人工确认，编译直接用该页面推导 PO，不再看标题。
- **绑定指向的 PO 消失**（改名/下线）→ `stale_po`，用例不执行并提示重新绑定。
- **绑定到无 PO 的页面** → `blocked_no_po`，`ready=False`，进缺口清单，**不会退回规则猜一个无关流程**。这是"宁可不跑也不假跑"的硬约束。

编译结果里的 `binding` 字段：

```json
{
  "kind": "ui_po", "pageId": "page:mall:/login", "pageName": "登录", "pagePath": "/login",
  "poName": "登录流程", "source": "human", "confidence": 100, "needsReview": false,
  "risk": "confirmed", "poSource": "human",
  "reason": "已绑定页面「登录」，使用流程「登录流程」"
}
```

`risk` 取值：`confirmed`（人工确认）/ `guess`（规则猜的）/ `mismatch`（规则认为不该走 UI 却被 PO 命中）/ `blocked_no_po` / `stale_po` / `none`。

## 3. 质量指标：四层 + 闸门

### 3.1 为什么不能只设"通过率"

单看通过率有三个致命问题：

1. **分母可操纵**——只挑稳定用例跑，通过率就上去了；
2. **假通过不区分**——跑了无关流程也算通过；
3. **不告诉你缺什么**——100% 通过可能意味着"只覆盖了 5% 的场景"。

所以指标设计成四层，**上层是下层的前提**：绑定不可信，结果层就没意义。

### 3.2 四层指标定义

#### L1 有效性（闸门层）

| 指标 | 公式 | 实测 | 目标 |
|---|---|---|---|
| 场景去重率 | 1 − 唯一标题数 / 功能用例数 | 94.5%（343/363 是副本） | < 20% |
| 绑定确认率 | 已人工确认 / 应绑用例（ui_* 三类） | 15.8%（19/120） | ≥ 90% |
| 断言密度 | ready 用例断言总数 / ready 用例数 | 3.89 | ≥ 2 |
| 有效可执行率 | `ui_po` 条数 / 功能用例数 | 7.7%（28/363） | 持续提升 |

> 绑定确认率的分母用 **120（应绑用例 = ui_po + ui_page_no_po + ui_ambiguous）** 而不是 363：220 条接口类用例本来就不该绑页面，8 条人工用例也不需要页面，算进去会稀释指标。

#### L2 结果层

| 指标 | 公式 | 实测 |
|---|---|---|
| 原始通过率 | 通过 / 执行 | 97.8% |
| **有效通过率** | 通过（仅 risk ≠ mismatch/blocked/stale）/ 有效执行 | 97.0%（132 次） |
| 无效率 | 无效执行 / 总执行 | 64.0%（235 次 / 367 次） |
| 失败归因 | 按步骤 detail 归类：定位器/遮挡/断言/超时/其他 | 定位器 5、其他 1 |

**有效通过率才是能对外说的数字**，因为它剔除了"绑定存疑"的执行。132 次有效执行 vs 367 次总执行，前者才是能下结论的样本。

#### L3 稳定层

| 指标 | 公式 | 实测 | 目标 |
|---|---|---|---|
| flake 率 | 结果不一致用例 / 多次执行用例 | 5.6%（6/108） | ≤ 2% |
| 耗时 P50 / P95 | 执行记录 durationMs 分位 | 5.7s / 12.2s | P95 ≤ 10s |

flake 明细可直接下钻：TC-1001 出现 16 次通过 + 2 次"部分可执行"——这类通常是环境/时序问题，不是产品 bug。

#### L4 覆盖层

| 指标 | 公式 | 实测 | 目标 |
|---|---|---|---|
| 页面 PO 覆盖率 | 有 PO 的页面 / 总页面 | 34.1%（14/41） | P0 页面 100%，全站 ≥ 60% |
| 页面用例覆盖率 | 被用例覆盖的页面 / 总页面 | 29.3%（12/41） | ≥ 80% |
| 需求覆盖率 | 有关联用例的需求 / 总需求 | 待接入 | ≥ 90% |

### 3.3 闸门：结论能不能说出口

指标算出来了，还要判断**这次能不能下结论**。当前实现三个闸门（`GET /ui/quality` → `gates`）：

```python
if executed < 20:            "样本不足"
if assertionDensity < 1:     "断言密度过低"
if bindingConfirmRate < 80:  "绑定确认率不足，通过率不能作为结论"
```

任一不满足 → `trusted: false`，前端顶部显示黄色警示条，列出具体原因。实测当前输出：

```
结论暂不可采信
· 绑定确认率 15.8%（19/120）：多数用例仍按规则猜测的绑定执行，通过率不能作为结论
```

**建议再补一条（尚未实现）**：跳过率 > 20% 时也不可信——现在一次批次可能跳过 273 条只跑 15 条，不说明的话看起来像"全跑了"。

### 3.4 不要把这些当 KPI

明确的负面清单：

- ❌ **"通过率 100%"当团队 KPI** → 会驱动只跑稳定用例、把失败用例下线；
- ❌ **用执行条数衡量工作量** → 会驱动复制用例（当前 94.5% 重复很可能就是这么来的）；
- ❌ **用"自动化覆盖率"单一数字对外** → 必须同时给页面 PO 覆盖率和绑定确认率，否则是分母游戏。

正确的用法：**看有效通过率的趋势 + 缺口清单的收敛速度**。

## 4. 落地：可追溯、可维护、可人工修改

### 4.1 可追溯：从用例能走到页面，从页面能走回用例

**正向**（用例 → 页面 → 流程）：用例列表新增「绑定页面」列，显示页面名 + 风险色点，悬停看判断依据。

**反向**（页面 → 用例）：`GET /ui/coverage/pages` 返回每个页面的覆盖情况。

实测输出（节选）：

| 页面 | 路径 | 覆盖用例 | 可执行 | 可用流程 |
|---|---|---|---|---|
| 商品列表 | /admin/products | 39 | 0 | 无（缺口最大） |
| 用户管理 | /admin/users | 21 | 0 | 无 |
| 首页 | / | 10 | 10 | 首页浏览流程、商品搜索流程 |
| 售后管理 | /admin/aftersales | 10 | 0 | 无 |
| 收货地址 | /addresses | 8 | 8 | 地址管理流程 |

这张表回答了"改一个页面要回归什么"和"为什么这些页面跑不了"。

> 顺带验证了规则的价值：最初"首页浏览流程"没配标题线索，10 条首页用例因为"多候选挑不出"被判为缺 PO；补上 `["首页","推荐","轮播","导航","运营位"]` 这一行后，10 条立刻变成可执行。**规则维护的成本是"加一行词"，收益是整批用例从不可执行变可执行。**

> 注：正式做法是把 `testcase --TESTS--> page` 写进 `trace_relations` 表（复用已有的 `proposed/confirmed/stale` 状态机和 `confidence`），这样在追溯图谱里能直接看到覆盖边。当前实现用页面路径聚合，不改 schema，成本更低；扩表方案见 §7 阶段四。

### 4.2 可维护：绑定失效能被发现

绑定会随系统演进失效，关键是**失效要显式**：

| 失效场景 | 系统行为 | 维护动作 |
|---|---|---|
| 页面路由改了 | 绑定 `pageId` 查不到 → 回落规则建议，`needsReview=true` | 体检页筛选"待确认"重绑 |
| PO 改名/下线 | `risk=stale_po`，不执行 | 改绑到新流程 |
| PO 实现改动 | 绑定不动，自动用新实现 | 无需动作（这是绑页面的收益） |
| 用例标题改了 | 人工绑定不受影响；规则建议会变 | 无 |
| 新增页面 | 出现在下拉里，`poNames=[]` | 写该页 PO 后自动转为可执行 |

**"绑页面不绑 PO"的直接收益**：14 个 PO 重构时，363 条用例的绑定一条都不用改。

### 4.3 可人工修改：一个动作说清楚

#### 单条改绑（用例列表 / 体检页 → 改绑定）

1. 点「绑定页面」或「改绑定」；
2. 弹窗里选页面（按业务域分组，41 个页面）；
3. 弹窗实时反馈：**该页面可用流程**（绿色 = 建议采用）、**无 PO 提示**、**意图冲突警告**；
4. **一页多流程时必须选一个**（单选，未选时「保存并确认」禁用）——例如 `/cart` 同时是「购物车流程」和「购物车结算流程」的入口，不选就无法确定跑什么；
5. 保存 → 立刻生效（下次编译按新绑定推 PO + 指定流程），不需要重新生成脚本。

写入用例文档的三个字段共同决定行为：

| 字段 | 值 | 编译时行为 |
|---|---|---|
| `pageId` + `poName` | 都有 | 直接用指定流程，`risk=confirmed` |
| `pageId` 有、`poName` 空 | 页面单流程 | 自动用该流程 |
| `pageId` 有、`poName` 空 | 页面多流程 | `blocked_ambiguous`，不执行（要求人选） |
| `pageId` 有、页面无 PO | — | `blocked_no_po`，不执行，进缺口清单 |

意图冲突警告的触发条件：这条用例被规则判为 `api`/`manual`，但用户选了 UI 页面。提示原文：

> 规则判断这条用例更像**接口/数据校验**。绑到 UI 页面后流程仍会跑通，但**不会验证金额、库存、字段这类页面看不到的东西**，通过结果不具备证明力。如果确实要走 UI，请确认断言覆盖了页面可见的结果。

这条警告是必要的——它把"人可以改，但改错会被指出来"这个约束显式化。

#### 批量改绑（体检页）

三种批量方式：

| 动作 | 行为 | 适用 |
|---|---|---|
| 全选 + 按建议确认 | 每条用各自的 `suggestPageId` 写入 | 快速走完 80% 的规则建议 |
| 全选 + 指定页面 → 应用到选中 | 全部绑到同一页面 | 一批同页面用例（如"商品列表"39 条） |
| 解除绑定 | 清空 `pageId`，回到规则建议 | 发现绑错时 |

实测：选中 17 条 `ui_po` → 按建议确认 → 确认率从 0.8% 升到 14.2%，`risk=confirmed` 17 条，`ready` 不变（289），**零回归**。随后又确认了 2 条（1 条进缺口清单），当前 19/120 = 15.8%。

#### 改绑后验证不回归

确认 TC-1001 → 真实执行：**通过，7 步，断言 2/2，7 张截图 + 1 段视频**。

确认 TC-1024（会员等级正确展示）→ 绑到"会员管理"页 → 该页无 PO → `ready=False`、`risk=blocked_no_po`、`pageObject` 为空。**它不会再假装能跑。**

### 4.4 执行策略联动：不确定的用例不跑

批量执行新增开关 `onlyConfirmed`（前端「只跑已确认绑定」）：

```json
POST /api/v1/ui/run-batch
{ "limit": 30, "maxWrite": 0, "onlyConfirmed": true }
```

实测结果：**执行 15 条、15 条通过、跳过 273 条**，跳过原因逐条写明：

> 绑定未人工确认（仅规则推断），本次限定只跑已确认绑定的用例

这是把指标落到执行上的关键一步：**没确认测哪个页面的用例不进队列**，从源头掐掉假通过。

### 为什么这些字段放在用例文档里而不是单独建表

- 用例本身就是 JSONB 文档，`PUT /testcases/{id}` 天然支持改；
- 导入/导出 Excel 时绑定跟着走，不会出现"用例迁走了绑定丢了"；
- 一个用例只有一个主页面，不需要多对多表；
- 反向查询（页面→用例）用 41 个页面对 363 条用例做内存聚合，耗时 < 10ms，不值得为它建索引。

## 6. 迁移路径（不要一次切换）

现在处于阶段一。四个阶段，每阶段都可回滚：

| 阶段 | 做什么 | 对执行的影响 | 当前状态 |
|---|---|---|---|
| 一 | 规则产出建议，`risk` 标记可见，编译保持旧行为 | 零变化（289 ready） | ✅ 已完成 |
| 二 | 人工确认 Top 用例（P0 + 高频模块），确认的按新绑定执行 | 确认的用例行为改变，其余不变 | 进行中（18/120） |
| 三 | 批量执行默认 `onlyConfirmed=true` | 未确认用例不进队列，执行条数下降、结论可信度上升 | 开关已就绪，未默认开启 |
| 四 | 关闭 `match_po` 兜底；未确认用例一律不执行 | 要求确认率 100%，否则执行量骤降 | 待前两阶段收敛 |

**为什么不一上来就强制**：当前 80% 的用例没有人工确认过，直接强制会让可执行用例从 289 掉到 17，业务方会认为"系统坏了"。先让缺口可见、让人愿意确认，再收紧闸门。

阶段四之前必须解决的一件事：**85 条"缺 PO"用例需要真的写出 PO**，否则确认率永远到不了 100%（人会卡在这一类上）。

## 7. 待解决与明确不做

### 待解决

1. **用例重复治理**（最高优先级）：363 条里 343 条是副本。建议按 `(title, steps)` 指纹去重，保留一条主用例 + 在 `relatedRequirementIds` 里记录它服务过的所有需求。做完这一步，"场景数"才从 363 变成 69，覆盖率才有意义。
2. **缺 PO 的 85 条**：集中在管理端（商品列表 39、用户管理 21、售后管理 10）。要么补 PO，要么明确"管理端不做 UI 自动化，走接口"。
3. **需求覆盖率**：需要 `requirement --COVERED_BY--> testcase` 的边，当前只有 `relatedRequirementIds` 数组，没有反向索引。
4. **失败自动归因**：现在按 detail 文本正则归类，应该由断言引擎直接产出 `failureType` 字段。
5. **跳过率闸门**：批次跳过 > 20% 时结论不可信，需加进 `gates`。

### 明确不做

- ❌ **不用 LLM 直接判断"这条用例测哪个页面"**：不可复现、不可审计，且错绑的代价是假通过。规则 + 人工确认更慢但可控。
- ❌ **不追求把 363 条全部变成可执行**：220 条本质是接口测试，硬转 UI 就是制造假通过。
- ❌ **不自动修复绑定**：页面路由变更时只标记失效，不猜新路径——猜错比不猜更贵。

## 8. 附录

### 8.1 分类规则表（`ui_bindings.py`）

**数据特征词 → api**

| 正则 | 理由 |
|---|---|
| 金额/total_amount/pay_amount/subtotal/运费/合计/小计 | 页面只展示结果，不暴露计算过程 |
| 库存/physical/locked/available/sold_count/超卖/扣减/释放 | 数据层不变式 |
| 脱敏/不回传/敏感字段 | 需检查响应体 |
| 幂等/idempotentKey/重复提交/重复支付 | 需接口重放 |
| SQL/数据库/表结构/索引/约束/CHECK/外键 | 库结构校验 |
| 返回 200/400/401/403/404/500、HTTP、接口、API、token | 接口契约 |
| 并发/行锁/读-改-写/竞态 | 需专用事务环境 |
| 精度/浮点/字符串不丢/序列化 | 序列化校验 |
| 不变式/一致性/快照 | 需比对库内字段 |

**视觉规范词 → manual**：文案一致 / 按钮顺序 / 布局 / 视口 / H5 / 响应式 / 样式 / 像素；探索 / 易用 / 体验；埋点 / 统计 / 报表；灰度 / 上线 / 发布 / 回滚。

**UI 强动作词**（出现时优先按页面归类，避免误判为接口）：点击 / 输入 / 勾选 / 上传；页面 / 弹窗 / 按钮 / 表单 / 列表页；展示 / 显示 / 可见 / 置灰 / 跳转。
