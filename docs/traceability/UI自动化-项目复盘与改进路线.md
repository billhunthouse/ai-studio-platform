# UI 自动化项目复盘与改进路线

> 用途：① 面试/汇报时讲清"这个项目怎么做、做出了什么效果"；② 自己迭代时知道下一步改什么、为什么。
> 所有数字均为 **2026-11-22 实测**，采集命令见第 10 章，可复现。
> 术语与实现细节见 `UI自动化执行-技术方案与使用手册.md`；演进史见 `UI自动化执行架构-设计说明.md`。

---

## 1. 一句话说清这个项目

> **把测试用例里的中文步骤，编译成可执行的 UI 指令，在真实浏览器里跑，每一步留下截图和视频，断言失败时告诉你"实际是什么"。**

它不是一个"能点按钮"的玩具，而是解决了三件事：

| 问题 | 传统做法 | 本项目做法 |
|---|---|---|
| 谁去执行 | 人工点，或写脚本 | 中文 → 关键字 IR → Playwright 执行 |
| 结果可信吗 | 脚本跑通就算过 | 1207 个真实断言（URL/文本/元素数），失败带实际值 |
| 出问题怎么查 | 看日志猜 | 每步截图 + 整段录屏 + 最终页面文本 |

| 断言 | **182 / 182 全过** |

| 证据产出 | **565 张截图 + 53 段视频**（565 步，100% 覆盖） |
| 真实写操作 | 3 条（真实创建订单，可用订单号回查业务库） |
| 媒体占用 | 本轮 119.9 MB，累计 144.1 MB / 5 GB |

### 2.3 稳定性与失败画像（历史 296 次单条执行）

| 指标 | 数值 | 解读 |
|---|---|---|
| 被执行过的用例 | 120 条 | 其余用例还没有执行样本 |
| 结果不稳定的用例 | **6 条（5%）** | 同一用例多次执行结果不一致 = flake 候选 |
| 历史失败 | **7 次**（296 次单条执行） | 其中 6 次有失败步骤明细，**5 次是"找不到元素"** |

> 这条很重要：**当前主要矛盾不是"测不出 bug"，而是"脚本自己会挂"**。改进优先级应该跟着这个走。

## 3. 它是怎么跑起来的（六层）

```
① 用例层   中文步骤 + 预期结果（363 条，平台已有）
              ↓
② 编译层   抽象步骤先拦截 → PO 匹配（命中就整体替换）→ 关键字编译 → IR
              ↓
③ 执行层   浏览器池（1 Chromium + N context）→ 9 个白名单关键字 → 7 种断言 → 快速失败
              ↓
④ 证据层   每步截图 + 整段视频 + 签名 URL + 5 GiB 滚动淘汰
              ↓
⑤ 编排层   单条同步 / 批量后台任务 / CLI；轮转取样、写配额、分段落库
              ↓
⑥ 展示层   执行记录（倒序）+ 批次下钻 + 用例列表门控 + 单条回放
```

### 3.1 编译层：把"人话"变成"指令"

三层过滤，顺序不能反：

1. **抽象步骤先拦截**。像"按验收标准逐项核对""查询订单总金额是否等于…"这类句子，**直接判定为非 UI 操作**，分类标注（`design_check` / `db_verify` / `security_probe` / `business_flow`），不硬转成假点击。
2. **PO 匹配**。标题关键词优先（"下单""支付""售后"），模块兜底。命中后，整条用例的步骤**被 PO 的真实操作序列替换**（含业务断言），原中文步骤只作为"测试意图"保留。
3. **关键字编译**。未命中 PO 的走正则 + 语义定位器词典："点击登录" → `click` + `button:has-text('登录')`。

> **为什么 PO 是"整体替换"而不是"拼接"**：拼接会保留前面"输入正确账号密码"这种模糊步骤，编译出来是 `{{TEST_VALUE}}` 占位，永远停在"部分可执行"。这是踩过的坑。

### 3.2 执行层：只认 9 个关键字

`nav / click / fill / select / check / assert / wait / scroll / screenshot`

- **不 eval 用户文本**，未知关键字标 `blocked` 跳过——安全和可审计的底线；
- 定位失败不抛框架异常，直接返回"找不到元素：xxx"；
- 点击被抽屉/toast 遮挡时（真实站点最常见），自动降级 `force=True` 重试一次；
- 断言 7 种：`url / url_not / text / no_text / count / regex / text_not_empty`，失败必带**实际值**；
- 快速失败：某步失败立即终止，不再浪费后续步骤和磁盘。

### 3.3 证据层：默认留证，而不是"需要时再补"

- 每步一张 1440×900 截图 + 整段 800×500 webm（本批次 53 条实测约 2.26 MB/条）；
- `<img>/<video>` 带不了 Header，所以发 **HMAC 签名 URL**（12 小时有效），无签名 403、文件不存在 404、`../` 穿越被拦；
- 5 GiB 预算，超了按目录 mtime 从旧到新删，被删记录打 `mediaPruned=true`——**结论保留，只丢媒体**；
- 实测容量：2.26 MB/条 → 5 GiB 约存 **2260 条**执行记录（约 42 轮全量回归）。

### 3.4 编排层：三个入口一套内核

| 入口 | 形态 | 适用 |
|---|---|---|
| `POST /ui/run-one` | 同步 5~15s | 单条调试、演示 |
| `POST /ui/run-batch` | 后台线程 + 轮询 | 批量回归（页面默认 120 条） |
| `run_ui_batch.py` | CLI | CI / 出报告 |

批量的三个设计点：

1. **轮转取样**：按 PO 分桶轮转，60 条覆盖 12 个流程，而不是同一流程刷 60 次；
2. **写操作配额**：默认 3 条（页面 8），用完进 `skipped` 并写明理由——**不是静默丢弃**；
3. **分段落库**：第 1 条、每 10 条、最后一条各写一次，进程被杀也留已完成部分。

### 3.5 展示层：结果要能"看见"

- 执行记录按开始时间**倒序**，一个批次只占一行：`批量执行 · 53 条 · 565 张 / 53 段`；
- 点进批次 → 逐条用例 → 点行 → 该条的每步截图 + 视频 + 失败步骤；
- 用例列表加"自动化"列：`是` 才能点运行，`否` 置灰（避免点了报错）；
- 单条执行后可直接看"本次生成的脚本"——同一份 IR 既能跑，也能导出成独立 Python 文件。

## 4. 四个关键取舍（面试最容易被追问的地方）

| 决策 | 选择 | 放弃的方案 | 理由 |
|---|---|---|---|
| 用什么驱动 | **Playwright 1.65（Python Sync）** | Selenium / Cypress / Puppeteer | 自动等待是刚需（中文用例没有精确 wait）；`text=` 定位能直接吃中文；原生录屏；context 便宜 |
| 怎么"翻译"步骤 | **关键字 IR 中间层** | 生成代码直接跑 / LLM 直接操作浏览器 | 不 eval、可审计、可导出、可换框架；LLM 直接操作不可复现 |
| 怎么保证"不假" | **抽象步骤诚实降级** | 全部硬转成点击 | 74 条业务规则用例硬转 = 假自动化，通过率会骗人 |
| 资源怎么管 | **1 浏览器 + N context**，批量任务独占池 | 每条用例启停浏览器 / 全局共享一个 Browser | 启停最贵；sync API 绑线程，跨线程复用必崩（踩过） |

## 5. 成果与效果（可直接用于汇报 / 简历）

### 5.1 前后对比

| 维度 | 改造前 | 现在 |
|---|---|---|
| 执行真实性 | 接口固定返回"成功"，没有一行代码碰浏览器 | 真实 Chromium，53 条 565 步全部执行 |
| 断言 | 无 | **1207 个**真实断言，平均 3.33 个/条 |
| 证据 | 无 | 每步截图 + 整段录屏，可按批次回看 |
| 用例可执行率 | 0 | **79.6%（289/363）** |
| 失败定位 | 看日志猜 | 第 N 步截图 + 断言实际值 |
| 回归效率 | 53 条人工约 7 小时（按 8 分钟/条） | **6 分 12 秒** |

### 5.2 效率账（口径写清楚，防止被追问）

```
人工：1 条用例 ≈ 8 分钟（含环境、数据、截图、记录）
     53 条 ≈ 7.1 小时；60 条 ≈ 8 小时；289 条 ≈ 38.5 小时
自动：实测 6.8 秒/条 → 53 条 6.2 分钟；289 条 ≈ 32.8 分钟
```

- **本轮实测**：53 条 / 371.6 秒，有批次 ID 可查；
- 单条 P50 **6.8s**、P90 **11.3s**、P95 **18.9s**（同一批次 53 条，不是历史混合样本）；
- **全量 289 条**是**线性外推**（按实测均值），不是已经跑过——讲的时候要说明"按实测均值外推"；
- 人工 8 分钟是行业经验值，可换成你们团队的真实数据。

### 5.3 质量收益（比效率更值钱）

1. **可信**：断言基于真实页面，不是"接口 200 就算过"；做过反向验证（把页面改坏，断言确实失败）；
2. **可归因**：失败能定位到"第 17 步 点击立即购买 → 元素被规格抽屉遮挡"，而不是"用例失败"；
3. **可复用**：14 个 PO 流程被 289 条用例共享，改一处全生效；中文用例改动不需要动代码；
4. **可审计**：每次执行有 runId、时间、浏览器、步骤、截图、视频，能回答"上周三那次回归到底跑了什么"。

## 6. 当前短板（带证据，别自欺）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **固定等待吃掉大部分时间** | 897 个 wait 步共 1132 秒 + 2914 个非 wait 步 × 300ms 节流 = **33.4 分钟**，而全量实测约 32.8 分钟 | 执行时间的 ~95% 在"等"，不是在做操作 |
| 2 | **每条用例都重新登录** | 12 个 PO 流程里 11 个以 `flow_login` 开头，登录 5 步约 3.9s | 289 条里约 250 条重复登录 ≈ 16 分钟浪费 |
| 3 | **flake 无治理** | 120 条执行过的用例里 6 条结果不一致（5%） | 失败要先人工判断"是不是抖动"，降低信任 |
| 4 | **失败不分类** | 历史 7 次失败，6 次可定位到步骤、其中 5 次是"找不到元素"，靠人看 | 无法回答"失败里有多少是产品 bug" |
| 5 | **元素库是死的** | 39 个元素只登记，编译链路完全不查它 | 维护者以为改了有用，实际无效 |
| 6 | **录制回放是模拟的** | 前端定时器回放 5 条写死步骤，未接 codegen | 演示时容易被戳穿，也别写进简历 |
| 7 | **任务表在内存** | `JOBS` 是进程内 dict | 后端重启丢进度；多实例不共享 |
| 8 | **写操作真落库** | 3 条真实订单/批 | 演示环境可接受，长期会污染数据 |
| 9 | **无 CI、无并发、无重试** | 全靠页面点；串行 1 worker | 无法做发布门禁；33 分钟无法压缩 |
| 10 | **无精准回归** | 289 条全跑 | 改一个页面也要跑 33 分钟 |

## 7. 改进路线

排序原则：**先修"可信和快"（影响每次使用），再修"体系和规模"（影响能不能长期用）**。

### 7.1 P0 — 本周就能做（投入小、收益立刻可见）

#### ① 固定等待 → 事件驱动等待

- **动作**：`wait(1500)` 改为 `wait_for_url` / `wait_for_selector` / `expect_response`；节流 300ms → 80ms（或按动作类型区分：点击后 150ms、导航后 0）
- **依据**：Playwright 本身有 actionability 自动等待，硬 wait 是双保险变成双浪费
- **预期**：单条 6.8s → **3.5~4.5s**；全量 33 分钟 → **16~20 分钟**
- **风险**：偶发竞态变多 → 必须同时上"失败重试 1 次"（见 ④）
- **验收**：60 条批次总耗时下降 ≥30%，通过率不降

#### ② 登录态复用（storage_state）

- **动作**：首次登录后 `context.storage_state(path=...)`，后续 context 复用；登录流程单独保留 1 条用例做冒烟
- **预期**：再省 2.5~3.5s/条（与 ① 有重叠，合计目标：全量 ≤12 分钟）
- **风险**：token 过期/单点登录 → 复用失败自动回退到真实登录

#### ③ 失败自动归因

- **动作**：失败时按规则打标签：`LOCATOR`（找不到元素）/ `INTERCEPT`（被遮挡）/ `TIMEOUT` / `ASSERT`（断言不成立 → 疑似真 bug）/ `ENV`（打不开页面）
- **价值**：把"7 次失败"从"都是红的"变成"6 次脚本问题、0 次产品问题"，这才是能对外的结论
- **验收**：批次详情页展示"失败分类"饼图/计数

#### ④ flaky 隔离 + 重试

- **动作**：失败自动重试 1 次（记录 `retried=true`）；同一用例近 10 次结果不一致 → 标 `quarantined`，不进主回归，单独看板
- **验收**：flake rate 从 5% → <2%，重试后通过的要标"不稳定通过"

### 7.2 P1 — 一个月（体系化）

#### ⑤ 打通追溯中心，做"变更影响 → 精准回归"（**最有价值的一条**）

平台已经有"需求 → 页面 → 接口 → 表"的追溯关系（trace 中心，41 个页面 / 137 个接口 / 37 张表）。而现在跑 UI 用例是"全量盲跑"。

- **动作**：给用例加 `pageId` 绑定（或在 PO 上声明 pageId），执行前调 `/trace/impact/forward` 拿到本次改动影响的页面，只跑这些页面对应的用例
- **预期**：一次发布回归从 33 分钟 → **3~5 分钟**，且"为什么跑这 20 条"可解释
- **为什么值钱**：绝大多数团队的 UI 自动化死因是"太慢，最后没人跑"。精准回归是让它活下来的关键，也是这个平台区别于通用框架的地方

#### ⑥ 元素库接入编译链路

- `_locator_for()` 先查 `uiElements`（39 个，按页面/名称），命中则用登记的 selector，未命中再走语义词典
- 好处：定位器集中管理，前端改版只改元素库；不再是"PO 里散落硬编码"

#### ⑦ CI 门禁

- PR 触发：冒烟子集 20 条（目标 <3 分钟）→ 不通过不给合
- 主干/每日：全量 289 条，出 HTML 报告
- 落地方式：CLI 已具备，套 GitHub Action / Jenkins 即可

#### ⑧ 测试数据工厂

- 下单/支付前自动造专属数据（手机号/商品前缀带时间戳），执行后清理；或接影子库
- 目标：写操作从"配额止血"变成"可反复跑不污染"

#### ⑨ 并发分片

- 按 PO 分片，4 个 worker，各占独立 browser；写操作用例强制串行互斥
- 预期：33 分钟 → **9 分钟**（与 ① 叠加后可到 4~5 分钟）

### 7.3 P2 — 一个季度（能力上限）

| 能力 | 做法 | 价值 |
|---|---|---|
| 定位器自愈 | 主定位失败时尝试备用（文本/role/邻近节点），成功则记录"已漂移"待人工确认 | 降低维护成本，前端小改版不炸 |
| 视觉回归 | 关键页面截图做像素/结构 diff（阈值+遮罩动态区） | 抓"功能没坏但样式崩了"这类 UI bug |
| LLM 辅助编译 | 抽象步骤 → 生成候选定位器 + 步骤建议，人工确认后入库 | 把 74 条不可执行降下来；**注意是"辅助编译"，不是"LLM 直接点"** |
| 报告与协作 | HTML 报告 + 失败推送到 IM + 一键建缺陷单（带截图/视频/步骤） | 闭环：执行→发现→提单→修复→回归 |

### 7.4 明确不做（体现判断力）

| 不做 | 原因 |
|---|---|
| 让 LLM 直接操作浏览器跑回归 | 不可复现、不可审计、失败无法归因，无法作为发布依据 |
| 追求 100% UI 覆盖 | 分层测试：接口测业务逻辑，UI 只测关键链路。74 条业务规则用例就该用接口/DB 断言 |
| 自研测试框架 | `pytest + playwright` 生态足够，重复造轮子只会增加维护面 |
| 追求"零维护" | 前端必然变，定位器必然腐化；目标应是"腐化可控、发现得快" |

## 8. 你可能没考虑到的 8 个盲区

> 这些不改也能跑，但一旦要"给团队用/给面试官看"，就会变成短板。

**① 只有通过率，没有质量度量**
通过率高不代表测得好。至少要四个指标：**flake rate**（抖动率）、**失败归因分布**（脚本问题 vs 产品问题）、**可执行率**、**执行时长 P95**。现在只有一个"通过率 100%"，反而显得可疑。

**② 用例 ↔ 页面的绑定是"猜"出来的**
`match_po()` 靠标题/模块关键词匹配。用例标题改一个字，可能就匹配到别的流程。没有显式绑定，就做不了精准回归、做不了覆盖率统计。

**③ 环境依赖硬编码**
`BASE_URL = "http://127.0.0.1:5174"` 写死在代码里。要上测试环境/预发，得改代码重部署。应该走配置（env/项目级配置），并支持多环境切换。

**④ 权限与审计**
"允许真实写操作"只是请求里一个 `force=true`。谁都能跑真实下单。至少要：写操作按角色限制 + 谁跑的写操作留审计日志。这在企业里是必答题。

**⑤ 证据的生命周期**
截图/视频在 `/tmp`，5 GiB 后淘汰。但"发布评审要查三个月前的回归证据"就查不到了。应该有归档策略（重要批次转对象存储）或"结论永久、媒体 30 天"的明确定义。

**⑥ 失败到缺陷的闭环没打通**
现在失败只停在"执行记录里有一条红的"。没有推送、没有建单、没有"修复后自动回归验证"。自动化只做了一半——发现问题，没做闭环。

**⑦ 反向验证没制度化**
v2 重构时做过一次 mutation test（故意改坏页面看断言是否失败），效果很好，但只做了一次。应该固化成"每次新增断言类型/P0 流程都做一次反向验证"，否则永远不知道断言是不是纸糊的。

**⑧ 没有"测试左移"的接口**
UI 用例只在发布前跑。其实接口契约（137 个 API）变更时，就能推断哪些 UI 流程会受影响——如果接口和页面有追溯关系，可以在开发提交阶段就预警。

## 11. 一页总结（汇报用）

- **做了什么**：把 363 条中文测试用例接进真实浏览器执行，289 条可直接跑，1207 个真实断言，每步留证。
- **怎么做的**：编译层（抽象步骤拦截 + PO 折叠 + 关键字 IR）→ 执行层（浏览器池 + 9 关键字 + 7 断言）→ 证据层（截图/视频/签名 URL/预算淘汰）→ 编排层（单条/批次/CLI）。
- **效果**：53 条 6 分 12 秒跑完（人工约 7 小时），53 条全通过，565 张截图可逐步回放，失败能定位到具体步骤和实际值。
- **知道自己的短板**：95% 时间在固定等待、5% 用例结果不稳、74 条跑不了、写操作污染数据、没有 CI 和精准回归。
- **下一步**：先做"事件驱动等待 + 登录态复用 + 失败归因 + flaky 隔离"（一周），再打通追溯做精准回归（一月），最后上自愈定位与视觉回归（季度）。
