## 1. 功能点拆分与覆盖

### 1.1 拆分口径

功能点取「需求的功能描述按顿号拆出的最小业务动作」，不是页面也不是接口。例如：

| 需求 | 功能描述 | 拆出的功能点 |
| --- | --- | --- |
| V1-FR-002 | 用户增删改查、启禁用、重置密码 | 用户增删改查 / 启禁用 / 重置密码 |
| V2-FR-012 | 申请、列表、详情、凭证上传 | 申请 / 列表 / 详情 / 凭证上传 |

52 条需求共拆出 **94 个功能点**，全部落库到 `requirements.points`（jsonb），可逐个勾选验证。

### 1.2 实体盘点

| 层 | 数量 | 来源 | 说明 |
| --- | ---: | --- | --- |
| 需求 | 52 | `02-requirements.md` | V1 24 条 + V2 26 条 + EXT 2 条 |
| 功能点 | 94 | 同上（拆解） | 平均每条需求 1.8 个 |
| 功能页面 | 41 | `04-page-map.md` | C 端 20 + 管理端 21（含 AI 浮窗） |
| 接口 | 137 | Java 源码扫描 | 24 个 Controller 的真实端点 |

## 2. 关联关系

### 2.1 已建立的关系

共 **624 条**，四类关系串起完整链路：

| 关系 | 方向 | 条数 | 来源与置信度 |
| --- | --- | ---: | --- |
| `SPLITS_INTO` 拆分为 | 需求 → 页面 | 79 | SPEC 95（PRD 页面列） |
| `TRIGGERS` 调用接口 | 页面 → 接口 | 175 | SPEC 95（页面地图）147 + HUMAN 100（人工指定）18 + AI_INFER 80（推断）10 |
| `EXPOSED_BY` 由代码实现 | 接口 → 代码 | 137 | CODE_SCAN 95（注解扫描） |
| `READS_WRITES` 读写数据表 | 接口 → 表 | 234 | CODE_SCAN 95（Mapper 调用）225 + HUMAN 100 9 |

**来源分级是真的在用**：不是所有关联都当事实。`AI_INFER` 的 10 条带 `status=proposed`，
在界面上可以逐条确认或否决；`HUMAN` 的 27 条是路径相似度算不准时人工指定的
（典型如 `/admin/auth/me` 与 `/api/me` 路径几乎相同但分属管理员与会员两套身份）。

### 2.2 关系建立过程中修掉的 3 个扫描器缺陷

| 缺陷 | 表现 | 修法 |
| --- | --- | --- |
| 数组注解路径被漏扫 | `@PostMapping({"/api/auth/login","/api/auth/phone"})` 整个方法解析失败，少 1 个端点 | 正则改为整段捕获注解参数，再逐个展开 |
| Javadoc 关联表被整句当表名 | `关联表：admin_user；依赖 PermissionQueryService` 被拆成一张不存在的表，导致管理员登录没有表关联 | 分号也作为终止符 |
| 跨轮残留孤儿实体 | 解析规则修正后，上一轮扫出的伪端点 `POST /` 一直留在库里，统计永远对不上 | 写库前按本轮结果清理未产出的接口/代码实体 |

### 2.3 文档与代码的漂移

| 方向 | 数量 | 含义 |
| --- | ---: | --- |
| 页面地图有、代码里没有 | 0 | 文档没有虚构接口 |
| 代码里有、页面地图没有 | 25 | 页面地图只记「主要调用」，辅助端点（文件预签名、仓库 CRUD、令牌刷新、移动端 `/api/auth/phone`）没登记 |

这 25 个接口本来会让 70 条用例无法归属需求，现已补上归属（其中 15 条人工指定、10 条按路径相似度推断待确认）。

## 4. 抽样验证：预期是否被真实实现满足

### 4.1 验证方式

启动真实后端（`shang-server` jar，端口 8086，连 55434 PG / 56379 Redis），
对 **57 条 GET 类正向用例**逐条构造请求实跑，按 rule.md §3.6 三要素判定
（协议层 HTTP + 业务层 code + 数据层 data 非空）。
管理端与 C 端分别用各自的身份令牌（`/admin/**` 用管理员，`/api/**` 用会员）。

### 4.2 结果

| 判定 | 条数 | 占比 |
| --- | ---: | ---: |
| 通过 | 47 | 82% |
| 预期与实际不符 | 4 | 7% |
| 无法执行（C 端账号无业务数据，取不到样本 id） | 6 | 11% |

### 4.3 不符的 4 条 —— 每一条都指向真实问题

| 用例 | 用例预期 | 实测 | 性质 |
| --- | --- | --- | --- |
| `GET_ADMIN_DICT_ITEMS-001` | HTTP 200 / code 0 | HTTP 500 / code 50000 | 用例缺必填参数 + 产品错误处理缺陷 |
| `GET_ADMIN_DICT_ITEMS_BY_CODE-001` | HTTP 200 / code 0 | HTTP 500 / code 50000 | 同上 |
| `GET_ADMIN_FILES_VIEW-001` | HTTP 200 / code 0 | HTTP 500 / code 50000 | 同上 |
| `GET_API_FILES_VIEW-001` | HTTP 200 / code 0 | HTTP 500 / code 50000 | 同上（C 端同一实现） |

**根因**：这 4 个接口的必填参数（`dictId` / `code` / `objectKey`）没有校验，
缺失时直接抛 NPE 被兜底成 500。对比 `POST /admin/auth/login` 缺 username 会正确返回
`HTTP 400 + code=40000`——说明不是全局约定，是这 4 个接口漏了 `@RequestParam(required=true)` 或参数校验。

**两件事要分开记**：
1. **用例缺陷**：这 4 条是「正向」用例，本不该省略必填参数，参数列写「不传可选过滤条件」
   把必填项也带过去了；
2. **产品缺陷**：即使参数缺失，也应返回 400 + BAD_REQUEST 而不是 500 + SYSTEM_ERROR。

### 4.4 附带确认的响应约定

实测确认本系统业务异常走 **HTTP 200 + body 数值码**（`GlobalExceptionHandler` 无 `@ResponseStatus`）：

| 场景 | 实测 |
| --- | --- |
| 评价回复缺 reply | HTTP 200 / code 40000 |
| 回复不存在的评价 | HTTP 200 / code 40400 |
| 回复超 500 字 | HTTP 200 / code 40000 |
| AI 助手正常提问 | HTTP 200 / code 50000（Agent 子服务未启动，环境依赖） |
| 未带 Token 访问受保护接口 | HTTP 401 / code 40100 |

这决定了后续所有负向用例的 `预期HTTP` 该怎么写，已在补充用例里按实测口径落笔并括注来源。

### 5.2 有意没做的事

- **没有动 424 条既有用例正文**：它们过了 lint、有评审记录，我不在这一轮批量改，
  只输出「哪 4 条要改、改成什么」；批量改写应由 lint + 评审流程走。
- **没有改 rel_type 枚举**：上一轮讨论的 6 → 5 收敛方案仍写在 `TODO.md`，涉及 624 条关系的数据迁移，需要单独排期。
- **没有把 UI 用例写成可执行 feature**：现有 Cucumber 步骤只覆盖登录/加购/结算/取消订单，
  补 29 个页面需要同时补 step 定义，工作量是另一轮的事。
