## 七、风险与对策

**R1. 293 条接口用例的预期是业务语义描述（如「状态变为 FROZEN」「仅返回必要字段」），引擎只能发请求、无法自动判定**

- 影响：跑完只会记「已执行」，需求仍不算验证通过；不处理则验证覆盖率卡在 40% 上下
- 对策：单列 J 批次人工裁定；把「返回 401」「状态变为 X」这类高频模式改写成可机读预期，下轮自动判

**R2. 被测后端单实例（8086），679 条接口用例只能串行跑**

- 影响：全量接口回归约需 5.7 小时机器时间
- 对策：批次间不并行；单批 ≤ 100 条，失败即停可定位；并发/幂等类用例移到压测环境

**R3. 100 条 DELETE 写操作用例默认跳过（保护演示数据）**

- 影响：删除类功能本轮无自动化结论，只能人工核对
- 对策：执行时按需勾选 force，或先对 commerce 库做快照再放开

**R4. 63 条 functional 用例没有被测接口**

- 影响：人工工时占总量 59%，是回归周期的主要瓶颈
- 对策：按业务域拆给不同执行人并行；优先只跑 P0/P1 正向步骤

**R5. 交易/支付用例会真实下单，污染演示数据**

- 影响：订单表继续膨胀，列表用例变慢甚至超时
- 对策：执行前记录订单表水位；执行后按 id 区间清理测试单；列表用例带时间窗参数

**R6. 固定验证码 123456 无环境开关（见需求整改报告漏洞 #1）**

- 影响：安全类用例会稳定判定「不符」，拉低通过率但不代表环境坏了
- 对策：本轮记为已知缺陷，不重复提单；修复后进 R1 复测

GET  /api/v1/prd/regression-plan/run/{jobId}        # 轮询进度
