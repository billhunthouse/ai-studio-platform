# 需求文档规范

> 版本：v1.1　　日期：2026-11-23　　适用范围：本平台所有项目（AI 生成的 PRD 与人工编写的 PRD 同一标准）
>
> 依据：ISO/IEC/IEEE 29148:2018《系统和软件工程——生命周期过程——需求工程》（取代 IEEE 830）的需求条目质量属性与 SRS 内容框架；验收标准采用 Gherkin 的 Given-When-Then 结构；用户故事采用 INVEST 原则。
>
> 一句话原则：**一条需求如果不能被验证，它就不是一条合格的需求。**

---

## 0. 一页速览

| 环节 | 产物 | 通过标准 |
|---|---|---|
| 需求提出 | 一句话背景 + 目标（含量化指标） | 目标可度量，不写"更好用/更友好" |
| 需求拆解 | 功能需求条目 FR-xx | 一条只描述一个能力，带唯一编号 |
| 验证设计 | 每条 FR 至少 2 条验收标准 AC | Given-When-Then，含可断言锚点 |
| 非功能 | NFR 分节 | 全部量化，带测量方法 |
| 数据 | 字段级数据字典 | 类型/必填/取值范围/默认值/约束 |
| 评审 | 质量门禁 + 人工评审 | 12 项质量属性无否决项 |

**不合格需求的三条红线**：① 出现"快速/友好/尽可能/等"这类不可测措辞；② 验收标准无法回答"用什么断言证明"；③ 一条需求里用"和/以及/同时"并列了多个能力。

---

## 1. 定位：需求文档写什么、不写什么

需求文档描述**需要什么（What）**，不描述**怎么做（How）**，也不描述**什么时候做（When）**。

| 该写 | 不该写 |
|---|---|
| 角色、场景、业务规则、状态与迁移 | 类名、表名、算法、框架选型 |
| 输入输出的取值范围与校验规则 | 接口的具体实现顺序、SQL |
| 验收标准（可断言的结果） | 排期、人力、里程碑 |
| 非功能约束（性能、安全、兼容） | 测试用例步骤（那是测试设计） |

**容易混淆的边界**：

- 需求里可以出现"接口需要鉴权"（约束），但不能出现"用 JWT + Redis 黑名单"（设计）。
- 需求里可以出现"列表分页，每页默认 20 条，最大 100 条"（规则），但不能出现"用 MyBatis-Plus 分页插件"（实现）。

## 2. 需求条目的 12 项质量属性

这是评审的判据表。**任一项不通过，该需求条目打回**,不允许"先合入后补"。

| # | 属性 | 判据（自检问题） | 常见失败表现 |
|---|---|---|---|
| 1 | 必要性 | 删掉这条，系统还能满足业务目标吗？ | 为"以后可能要用"而写 |
| 2 | 无歧义 | 两个人独立读，理解是否完全一致？ | "适当的提示""合理的超时" |
| 3 | 完整性 | 是否还需要读者去猜输入、输出、条件？ | 只写正常流程，没写失败分支 |
| 4 | 单一性 | 是否用"和/以及/同时"并列了多个能力？ | 「登录、失败锁定、登出」合成一条 |
| 5 | 可行性 | 现有技术栈与数据条件下能否实现？ | 依赖不存在的外部服务 |
| 6 | 可验证 | 能否写出断言？用什么证明它被满足？ | 验收标准是"功能正常" |
| 7 | 一致性 | 与其它需求的术语、数值、规则是否冲突？ | 一处写锁定 15 分钟，一处写 30 分钟 |
| 8 | 可追踪 | 能否向上追到来源、向下追到设计与用例？ | 需求无编号、无来源文档 |
| 9 | 有界性 | 是否全部量化，没有"快速/友好/尽可能"？ | "响应要快" |
| 10 | 正确性 | 需求提出方是否确认过？ | 由技术侧臆测业务规则 |
| 11 | 无设计偏好 | 是否只描述做什么，没锁定怎么做？ | "用 Redis 存验证码" |
| 12 | 许可性 | 是否违反法规、行业规范或组织约束？ | 明文存储身份证号 |

> 落地建议：把这张表做成评审打分卡，每条需求逐项勾选；同一项目连续两个迭代使用后，返工率通常明显下降。

## 3. 文档骨架

一份合格的需求文档必须包含下列章节。标注**必填**的缺一不可。

| 章节 | 必填 | 内容要素 | 常见错误 |
|---|---|---|---|
| 1. 文档信息 | 是 | 版本、作者、评审人、变更记录、关联需求编号 | 无版本，改了什么查不到 |
| 2. 背景与目标 | 是 | 业务现状、痛点、目标（**量化指标**）、不做的后果 | 目标写"提升体验" |
| 3. 范围 | 是 | In Scope / **Out of Scope** 两张清单 | 只写做什么，不写不做什么 |
| 4. 角色与权限 | 是 | 角色清单、每角色可见入口与操作、数据范围 | 只写"管理员/用户"两角色 |
| 5. 术语表 | 是 | 术语、定义、别名、禁止使用的同义词 | 同一概念三种叫法 |
| 6. 业务流程 | 是 | 主流程 + 分支流程 + 状态机（状态、事件、迁移、非法迁移） | 只画主流程 |
| 7. 功能需求 | 是 | FR-xx 条目（见 §4） | 条目里混入设计细节 |
| 8. 验收标准 | 是 | 每条 FR 的 AC（见 §5） | 陈述句，无法断言 |
| 9. 非功能需求 | 是 | 性能/安全/可用性/兼容性/可维护性（见 §6） | 一句"性能良好"带过 |
| 10. 数据与字段 | 是 | 实体、字段、类型、必填、取值范围、默认值、唯一性、脱敏要求 | 只有表名，没有字段语义 |
| 11. 异常与边界 | 是 | 空态、超时、并发、重复提交、越权、极限值 | 留空 |
| 12. 依赖与假设 | 是 | 外部系统、第三方服务、前提条件、失效后的降级 | 不写，出事互相甩锅 |
| 13. 遗留与待定 | 是 | 未决问题、责任人、决策截止时间 | 用"待定"掩盖没想清楚 |

> **Out of Scope 与"依赖与假设"是最常被省略、也最容易在验收时吵架的两节。** 不写清楚"这次不做"，范围就会在执行中无限膨胀。

## 4. 功能需求条目格式

### 4.1 模板

```text
FR-<模块>-<序号>  <动作>+<对象>+<结果>（一句话，不超过 40 字）

角色：        谁在操作（必须来自 §4 角色清单，不能写"用户"）
入口：        从哪个页面/菜单/接口进入（路由或接口路径）
前置条件：    数据状态 + 权限状态 + 环境状态（三选一以上，禁止一律写"已登录"）
触发动作：    一次用户操作或一次系统事件（只写一个）
业务规则：    编号列出，每条可判定（R1/R2/R3）
后置状态：    操作成功后数据/状态如何变化（含不可逆说明）
异常分支：    每个失败原因 → 系统反馈 → 数据是否回滚
关联接口：    METHOD /path（来自真实扫描，不得臆造）
关联数据：    表.字段（写入/读取哪些字段）
```

### 4.2 填写要求

| 字段 | 要求 | 反例 |
|---|---|---|
| 前置条件 | 必须体现**本条需求特有**的状态 | 「用户已登录且具备相应角色」（52 条需求全都这么写，等于没写） |
| 业务规则 | 每条带编号，可被 AC 引用 | 「按业务要求校验」 |
| 后置状态 | 明确哪些字段被改、改成什么 | 「更新数据」 |
| 异常分支 | 至少覆盖：参数非法、权限不足、状态不允许、资源不存在、并发冲突 | 留空 |
| 关联接口 | 必须能在接口清单里查到 | 编一个不存在的 path |

### 4.3 拆分粒度

一条需求只描述**一个能力**。判据：标题里出现"和/以及/同时/、"就拆。

```text
✗ V1-FR-001【登录】账密登录、失败锁定、登出          ← 三个能力混在一条
✓ FR-AUTH-001 管理员使用账号密码登录
✓ FR-AUTH-002 连续登录失败达阈值后锁定账号
✓ FR-AUTH-003 管理员主动登出并使令牌失效
```

拆分不是把文档写长，而是让**验收、缺陷归属、变更影响**都能定位到具体一条。

## 5. 验收标准（AC）写法

### 5.1 三种 AC 与适用场景

| 形式 | 适用 | 示例 |
|---|---|---|
| 规则导向（Rule-oriented） | 单字段校验、计算规则 | 「密码长度 8-20 位，须含字母与数字」 |
| 场景导向（Given-When-Then） | 有前置状态与结果变化的流程 | 见下 |
| 清单导向（Checklist） | 非功能、兼容性 | 「1440×900、1280×800、390×844 三档视口无横向滚动」 |

**默认使用 GWT**，因为它天然包含"前置数据"，能直接转成自动化用例。

### 5.2 GWT 模板

```text
AC-<FR 编号>-<序号>
Given  <可构造的前置状态：具体数据 + 具体权限 + 具体状态值>
When   <一个动作：一次点击/一次请求/一个事件>
Then   <可观察的结果：状态码 + 业务码 + 字段值 + 数据落库变化>
And    <副作用：日志、消息、其它端可见性>
```

### 5.3 可断言锚点（四级，至少命中两级）

| 级别 | 锚点 | 示例 |
|---|---|---|
| L1 传输层 | HTTP 状态码、Content-Type | `HTTP 401` |
| L2 业务层 | 业务码、提示文案 | `code=40104`，`msg=登录失败次数过多` |
| L3 数据层 | 表.字段 的精确值 | `identity.admin_user.last_login_at` 非空；`commerce.stock.locked_stock` +1 |
| L4 界面层 | 页面元素、路由、可见性 | 跳转 `/dashboard`；侧栏"商品中心"可见；toast 文案 |

> 只写"返回成功"或"提示正确"属于**弱断言**，不可接受：数据可能没落库，页面可能没刷新。

### 5.4 数量与覆盖要求

- 每条 FR **至少 2 条** AC：1 条正向 + 1 条负向/边界。
- 涉及写操作的 FR **必须**有 1 条数据层断言（L3）。
- 涉及状态机的 FR **必须**有 1 条非法迁移的 AC。
- 涉及鉴权的 FR **必须**有 1 条越权 AC（低权限/他人资源/跨端令牌）。

### 5.5 反例改造（本项目真实案例）

**原始写法**（无法验收）：

```text
AC-02 密码错误连续 5 次后，第 6 次被锁定 15 分钟
```

问题：锁定从哪一次开始计时？"15 分钟"从第 5 次失败算还是第 1 次算？解锁后计数是否清零？用什么断言？

**改造后**：

```text
AC-AUTH-002-1
Given 账号 admin 存在且状态 ENABLED，Redis 键 login:fail:admin 不存在
When  连续 5 次以错误密码请求 POST /admin/auth/login
Then  第 6 次请求返回 HTTP 401，code=40104，msg 含"15 分钟"
And   Redis login:fail:admin 存在，TTL 在 900s±30s 内
And   identity.admin_user.last_login_at 未变化

AC-AUTH-002-2（边界：计数的重置语义）
Given 已失败 4 次，距首次失败已过 14 分 50 秒
When  再次以错误密码登录
Then  计数变为 5 并**重新开始** 15 分钟锁定窗口（或明确写出"不重置"）
```

最后这条边界 AC，正是本项目当前实现的一个真实缺陷所在（TTL 只在首次失败时设置一次，导致"锁定 15 分钟"实际可能不足 1 分钟）。**写不出这条 AC，缺陷就永远不会被发现。**

## 6. 非功能需求（NFR）

NFR 必须量化，且写明**测量方法**。禁止出现"良好/较快/稳定"。

| 类别 | 必写指标 | 本项目基线示例 |
|---|---|---|
| 性能 | 单接口 P95/P99、目标 RPS、并发数、压测工具与数据量 | 读接口 P95 ≤ 200ms、写接口 ≤ 500ms（500 并发、思考时间 200ms、库存 1000+） |
| 容量 | 单表预期行数、增长速率、归档策略 | 订单表年增 200 万行，保留 3 年 |
| 安全 | 认证方式、令牌有效期、越权防护、敏感字段脱敏、密码存储算法 | access 15 分钟、refresh 7 天；手机号 `139****0001`；BCrypt |
| 可用性 | 可用性目标、单点故障、降级与熔断 | 99.5%/月；LLM 不可用时降级为 FAQ 检索 |
| 兼容性 | 浏览器/视口/系统版本清单 | Chromium 基线 + WebKit；1440×900 / 1280×800 / 390×844 |
| 可维护性 | 日志级别与保留、指标暴露、追踪 | 结构化日志保留 7 天，actuator 暴露 health/metrics |
| 合规 | 数据保留期限、个人信息处理、审计要求 | 操作日志保留 180 天，删除需留痕 |

> **反面案例**：本项目的"固定验证码 123456 可完成登录"被写进了验收标准，却没有写环境限定（仅 dev/demo 可用，生产必须关闭）。漏洞就是这样被"需求"合法化的。

## 7. 数据与字段约束（数据字典）

每个实体一张表，字段级写清约束。**只写表名不算数据字典。**

| 字段 | 类型 | 必填 | 取值范围/枚举 | 默认 | 唯一 | 脱敏 | 说明 |
|---|---|---|---|---|---|---|---|
| phone | varchar(20) | 是 | `^1[3-9]\d{9}$` | — | 是 | 是（中间 4 位） | 登录账号，注册即建档 |
| status | varchar(16) | 是 | `NORMAL`/`FROZEN` | `NORMAL` | 否 | 否 | 冻结后禁止登录与下单 |
| locked_stock | int | 是 | `>= 0` 且 `<= physical_stock` | 0 | 否 | 否 | 下单锁库存，支付后转扣减 |

**必须写明的约束类型**：类型与长度、必填性、枚举全集、数值上下界、唯一性、外键与级联行为、默认值、软删标记、审计字段、脱敏要求。

**不变式（Invariant）单独列出**，这是最容易出并发 bug 的地方：

```text
INV-01  physical_stock ≥ locked_stock ≥ 0
INV-02  available = physical_stock - locked_stock，且 available ≥ 0
INV-03  订单金额 = Σ(单价 × 数量) + 运费 - 优惠，误差 ≤ 0.01
```

## 8. 异常、边界与状态机

### 8.1 异常清单（每条 FR 至少归入 3 类）

| 类别 | 要写清的内容 |
|---|---|
| 参数非法 | 必填缺失、类型错误、长度越界、格式不符、枚举越界 |
| 权限 | 未登录、令牌过期、角色不足、越权访问他人资源、跨端令牌混用 |
| 状态不允许 | 当前状态不支持该操作（如非待发货订单发货） |
| 资源 | 不存在、已被删除、已被他人占用 |
| 并发 | 重复提交、并发修改同一条数据、库存竞争、幂等键冲突 |
| 依赖失败 | 下游超时、第三方不可用、MQ 积压、缓存击穿 |
| 极限 | 0 条/1 条/最大条数、分页越界、超长文本、超大文件 |

每一类都要写：**系统反馈什么（码/文案）+ 数据是否回滚 + 是否可重试**。

### 8.2 状态机

用表格表达，比文字可靠：

| 当前状态 | 事件 | 目标状态 | 触发者 | 副作用 | 非法迁移的处理 |
|---|---|---|---|---|---|
| PENDING_PAY | 支付成功 | PENDING_SHIP | 支付回调 | 锁库存转实扣、写销量 | — |
| PENDING_PAY | 超时（15 分钟） | CLOSED | 定时任务 | 释放锁库存 | — |
| PENDING_SHIP | 发货 | SHIPPED | 管理员 | 写运单号 | 非 PENDING_SHIP 发货 → 409，且不写库 |
| CLOSED | 支付成功 | —（禁止） | — | — | 拒绝并自动退款 |

## 9. 追溯、变更与生命周期

### 9.1 必填元数据

| 字段 | 说明 |
|---|---|
| 需求编号 | 全局唯一，`<项目>-<模块>-<序号>`，一经分配不得复用 |
| 来源 | 上溯到原始诉求（会议/文档/客户/缺陷） |
| 关联设计 | 接口、页面、表（由扫描结果回填，不得手填臆造） |
| 关联用例 | 覆盖该需求的用例 ID 列表 |
| 状态 | 见 §9.2，与"解析状态"分开 |
| 版本 | 每次实质修改 +1，记变更原因 |

### 9.2 需求状态机

```text
草稿 → 待评审 → 已批准 → 开发中 → 已实现 → 已验证 → 已关闭
                    ↑                    ↓
                    └──── 变更请求 ←──────┘
```

**关键区分**：`已实现`（代码有）与 `已验证`（用例通过）是两个状态。只有代码没有验证，不能标"已验证"；只有 PRD 解析完成，更不能标"已实现"。

> 本项目当前只有"已解析"一个状态，把"文档解析完"当成"需求已就绪"，导致 `已实现/已验证` 无法区分——这是 37.5% 行为覆盖率却没人报警的根本原因。

## 10. 自动质量门禁

下列规则可脚本化，建议在 PRD 落库前强制执行，不通过则不允许发布。

| 规则 | 检测方式 | 阈值 |
|---|---|---|
| 模糊词 | 正则：`快速|友好|尽可能|必要时|适当|及时|尽量|等` | 出现即拒绝 |
| 多条合并 | 正则：`和|以及|同时|并且`（标题内） | 出现即提示拆分 |
| 前置条件模板化 | 同一项目内 `precondition` 完全相同的占比 | > 30% 报警 |
| 验收标准无锚点 | AC 文本不含数字/状态码/字段名 | 占比 > 20% 拒绝 |
| 无 GWT | AC 以 `Given/When/Then/假设/当/那么` 开头的占比 | < 50% 提示 |
| 异常为空 | `exceptions` 数组长度 = 0 | 有写操作的需求出现即拒绝 |
| 单一性 | 一个 FR 关联接口数 | > 5 个提示拆分 |
| 可追踪 | 无关联接口且无关联页面的 FR | 出现即标记"不可测" |
| 非功能缺失 | 文档无 NFR 章节 | 拒绝发布 |
| 角色语义冲突 | 用户故事角色与功能名不匹配（如"访客"+"登出"） | 人工复核 |
| 验证覆盖 | 关联用例中"执行通过"的条数 | 0 条即标记"未验证"，不得转「已验证」状态 |

> 前十条校验**文档本身是否可评审**，最后一条校验**需求是否被证明**。
> 二者必须分开看：文档写得再全，用例一条没跑，需求也只是"看起来完成"。
> 本项目实测：文档门禁通过率 90.7%（498/551），验证门禁通过率 3.8%（2/52）——差距就在这里。

## 11. 评审清单

### 11.1 就绪定义（DoR，进开发前）

```text
[ ] 目标含量化指标，且能说明"不做会怎样"
[ ] Out of Scope 已明确列出
[ ] 每条 FR 只含一个能力，编号唯一
[ ] 每条 FR 的前置条件是本需求特有的，不是模板套话
[ ] 每条 FR 至少 2 条 AC，且都含 ≥2 级可断言锚点
[ ] 写操作有数据层断言；状态机有非法迁移 AC；鉴权有越权 AC
[ ] 异常清单覆盖 ≥3 类
[ ] NFR 全部量化，写明测量方法
[ ] 数据字典到字段级，不变式已列出
[ ] 依赖与假设已写，含降级方案
[ ] 关联接口/页面来自真实扫描，无臆造
```

### 11.2 完成定义（DoD，验收时）

```text
[ ] 代码已实现，且实现与 FR 的业务规则逐条对应
[ ] AC 全部有对应用例，且用例已执行通过
[ ] 数据层断言实际执行过（不是"应该会写库"）
[ ] 异常分支逐条验证过，含回滚验证
[ ] NFR 有实测数据（压测报告/扫描报告）
[ ] 需求状态更新为"已验证"，关联用例可追
```

### 11.3 评审会必问的五个问题

1. 这条需求删掉，业务会损失什么？
2. 这条需求怎么验收？用什么断言？
3. 失败的时候系统表现是什么？数据会不会脏？
4. 这条需求不做什么？（边界）
5. 有没有把设计决策写进需求？

## 12. 附录：完整样板

以本项目的登录需求为例，展示从"不合格"到"合格"的完整改写。

### 12.1 改写前（现状）

```text
标题：  【登录】账密登录、失败锁定、登出
目标：  让用户安全进入系统，并在失败尝试、令牌时效上具备可预期的行为。
前置：  用户已登录且具备相应角色
用户故事：作为顾客/会员，我希望失败锁定，以便让用户安全进入系统…
验收：  AC-01 使用正确账密登录返回 200 且拿到 accessToken
        AC-02 密码错误连续 5 次后，第 6 次被锁定 15 分钟
异常：  （空）
```

问题：三个能力混一条；目标是套话；前置条件自相矛盾（登录要求已登录）；把管理员的"失败锁定"归给顾客；异常为空；AC 无 GWT 无数据断言。

### 12.2 改写后

```text
FR-AUTH-001  管理员使用账号密码登录

角色：      管理员（admin 端）
入口：      /login → 提交表单 → POST /admin/auth/login
前置条件：  R1 账号存在且 status=ENABLED；R2 未被锁定（login:fail:<username> 计数 <5）；
            R3 密码以 BCrypt 存储
触发动作：  提交用户名+密码（一次）
业务规则：
  R1 用户名不存在与密码错误返回同一错误码，不泄露账号是否存在
  R2 登录成功清空失败计数
  R3 成功登录更新 last_login_at 并记录操作日志（含 IP、UA）
后置状态：  签发 access(15min)/refresh(7d)；admin_user.last_login_at = now；
            trace_audit_logs 新增一条 action=login,result=SUCCESS
异常分支：
  E1 密码错误 → HTTP 401 / code=40101，计数 +1，不写登录态
  E2 账号禁用 → HTTP 403 / code=403xx，不签发令牌
  E3 已锁定   → HTTP 401 / code=40104，提示剩余时间
关联接口：  POST /admin/auth/login
关联数据：  identity.admin_user(username,password,status,last_login_at)

AC-AUTH-001-1（正向）
Given admin/Admin@123 存在且 ENABLED，计数为 0
When  POST /admin/auth/login
Then  HTTP 200，code=0，data.accessToken 非空且可解析出 uid/clientType=admin
And   admin_user.last_login_at 在 5s 内更新
And   Redis login:fail:admin 不存在

AC-AUTH-001-2（负向 · 账号不存在不泄露）
Given 用户名 ghost_user 不存在
When  任意密码登录
Then  HTTP 401，code=40101，msg 与"密码错误"完全一致
And   不创建任何 admin_user 记录

FR-AUTH-002  连续登录失败达阈值后锁定账号

角色：      管理员
入口：      POST /admin/auth/login
前置条件：  R1 账号存在；R2 login:fail:<username> 不存在或 <5
触发动作：  以错误密码提交一次
业务规则：
  R1 失败计数以用户名为键，窗口期 15 分钟
  R2 计数 ≥5 时拒绝登录，返回 40104
  R3 锁定窗口自【首次失败】起算，还是自【达到阈值】起算，必须二选一并写明
后置状态：  计数 +1；达到阈值后该账号在窗口期内不可登录（正确密码也不可）
异常分支：
  E1 窗口期内正确密码 → 仍返回 40104（安全优先）
  E2 窗口过期 → 计数归零，可正常登录
关联接口：  POST /admin/auth/login
关联数据：  Redis login:fail:<username>（TTL 900s）

AC-AUTH-002-1（正向）
Given 账号 admin 未被锁定
When  连续 5 次以错误密码登录
Then  第 6 次返回 HTTP 401 / code=40104
And   Redis login:fail:admin 的 TTL ∈ [870, 900] 秒
And   admin_user.last_login_at 未变化

AC-AUTH-002-2（边界 · 窗口语义）
Given 已失败 4 次，距首次失败已过 14 分 50 秒
When  第 5 次以错误密码登录
Then  若规则为"自首次失败起算"，第 10 秒后即可再次尝试（锁定时长仅 10 秒）
      → 该行为不符合"锁定 15 分钟"的业务预期，应改为"达到阈值时重置 TTL"
And   无论采用哪种语义，都必须在 R3 明确写出，并有用例守护

AC-AUTH-002-3（负向 · 权限）
Given 账号已锁定
When  使用【正确密码】登录
Then  仍返回 HTTP 401 / code=40104，不签发令牌

FR-AUTH-003  管理员主动登出并使令牌立即失效

角色：      管理员
入口：      POST /admin/auth/logout
前置条件：  持有有效 accessToken
触发动作：  点击"退出登录"
业务规则：  R1 登出后该 accessToken 立即进入黑名单直至自然过期
            R2 客户端清除本地令牌
后置状态：  黑名单存在该 jti；再访问受保护接口返回 401
异常分支：  E1 令牌已过期 → 返回 200（幂等）；E2 无令牌 → 401
关联接口：  POST /admin/auth/logout
关联数据：  Redis token:blacklist:<jti>（TTL = 令牌剩余有效期）

AC-AUTH-003-1
Given 管理员已登录并持有 accessToken T
When  调用 POST /admin/auth/logout，随后用 T 访问 GET /admin/users
Then  登出返回 HTTP 200 / code=0
And   随后访问返回 HTTP 401 / code=40103
```

### 12.3 改写带来的直接收益

| 改写前 | 改写后 |
|---|---|
| 3 个能力 1 条需求 | 3 条独立需求，缺陷可归属 |
| 前置条件无法成立（登录要求已登录） | 前置条件可构造 |
| "锁定 15 分钟"无法验证 | 3 条 AC 覆盖阈值、窗口语义、正确密码仍拒绝 |
| 异常为空 | 6 个异常分支，均写明码值与数据影响 |
| 无数据断言 | `last_login_at`、Redis TTL、黑名单 jti 三处落库验证 |
